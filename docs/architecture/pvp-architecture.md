## 0. 结论先行（TL;DR）

| # | 结论 | 判断 |
|---|---|---|
| **1** | **通信层选 SSE，不选 WebSocket**。零第三方依赖硬约束下，SSE 是 stdlib 唯一零风险的服务器推送；PvP 流量模型天然「低频上行、高频下行」，完美匹配。手写 WS（RFC 6455 握手 + 分帧 + 掩码 + 关闭握手）要 1.5~2 人日且留长期维护债，收益不足以覆盖。 | 🔴 强立场 |
| **2** | **房间状态服务端权威 + `turn_seq` 乐观锁 + `client_msg_id` 幂等**。回合锁不能靠「长事务锁」——现有 `_process_message` 持 session 锁跨 2 次 LLM（2~4s），PvP 下直接雪崩。用乐观锁，锁持有期缩短到纯内存操作（<1ms）。 | 🔴 必做 |
| **3** | **2核2G 单机稳态容量 ≈ 250~350 个进行中房间（500~700 在线玩家）**。瓶颈是**线程数**（每 SSE 连接 1 线程），不是内存也不是 CPU；上游 LLM 并发闸门（32）在 300 房间下只用掉约 12，不构成瓶颈。 | 🟡 `[待实测]` |
| **4** | **PvP 单局 LLM 成本只有单人的 ~27%**（0.0087 vs 0.032 元，N=12），因为 NPC 生成（占单人成本 68%）整个消失。但**内容安全成本反超**（灰区率 30%→45%）。**合计 ≈ 0.019~0.036 元/局，中位 0.022 元 ≈ 2.2 分**，是单人含审核口径（0.040）的 **55%**。 | 🟢 反直觉但成立 |
| **5** | **PvP 的刷量风险比单人更高，不是更低**。双开自刷不受匹配限制：100 个号 ≈ **15.5 万元/月**（vs 单人 10.2 万）。第一道闸门是「同 device_fp / 同 ip/24 禁止互配」，直接掐死自刷。 | 🔴 必做 |
| **6** | **AI 代打无法被可靠检测**。所有技术手段（粘贴检测/节奏特征/统计指纹）都是「提高成本」而非「阻断」。困惑度 PPL 明确做不了（本地跑不动、云端无接口、中文判别力差）。**真正的解药在玩法设计：限时（45~60s）+ 强制回应对手原话**。 | 🔴 给设计侧的头号建议 |
| **7** | **「打码」可以做成游戏机制，且是本项目少数能把合规成本转成玩法资产的机会** —— 但必须满足三条硬约束，其中第一条是：**违规必须永远净亏**（命中即判 L0 + 文明度惩罚 + 归零判负）。绝不能让骂人有收益。 | 🟡 建议做，带约束 |
| **8** | **PvP 会让合规压力上一个台阶**：「人对人交互」把 release-plan 五要素自检从命中 3 个推到 4 个，让生成式 AI 登记从「可能要」变成「确定要」。**PvP 公开上线必须排在合规动作之后，这比单人模式更硬。** | 🔴 硬阻塞 |
| **9** | **数据层选 sqlite3**（stdlib 自带、WAL 模式、`threading.local()` 每线程一连接）。但 **NPC 记忆与天梯进度不迁移**，继续用 JSON —— 避免动到单人模式热路径，迁移风险 > 收益。 | 🟢 |
| **10** | **路线：M0 热座（3~5 人日）→ M1a 间接对抗（4~6）→ M1b 异步回合（4~6）→ M2 同步实时（15~22）**，合计 **22~33 人日 + 合规外部周期**。M0 是 9-15 大赛截稿前唯一来得及的，且一个人就能演示"两个人对打"，反而更适合参赛物料。 | 🔴 |

## 1. Q1 · 通信层

### 1.1 选型对比

| 方案 | 依赖 | 工作量 | 2核2G 适配 | 风险 | 结论 |
|---|---|---|---|---|---|
| **SSE（Server-Sent Events）** | **零**（纯 HTTP chunked） | 0.5~1 人日 | 每连接 1 线程（天花板见 §1.4） | 低（浏览器原生 `EventSource`） | ✅ **推荐** |
| 长轮询 | 零 | 0.5 人日 | 每次轮询短连接 | 低 | ✅ **作为降级通道** |
| 手写 WebSocket（stdlib） | 零 | 1.5~2 人日 happy path，生产可靠需 +1 | 全双工省一半连接 | **高**（掩码、分片、关闭握手、UTF-8 校验、并发安全，全是坑） | ❌ 否决 |
| `websockets` 库 | +1 依赖（纯 Python） | 1 人日整合 | 需 asyncio 事件循环，与现有 threading 模型混用 | 中（双运行时心智负担） | ❌ 收益不足 |
| FastAPI + uvicorn | +N 依赖 | 整体重写 | — | **违反「不许重写」铁律** | ❌ 否决 |

**决策：SSE 主信道 + REST POST 命令 + 长轮询自动降级。**

三条理由：
1. **零依赖是硬约束**（`server.py` 现状零第三方，这是它能在 2核2G 上跑起来、且能在网盘交付离线 demo 的根本原因）。SSE 的代价只有 chunked 编码 + 一个 `flush`，stdlib 全支持。
2. **PvP 流量模型天然匹配**：客户端→服务端只有「提交发言 / 心跳 / 举报」三种低频动作（分钟级），服务端→客户端才是高频（回合事件、对手 typing、倒计时、判定结果）。SSE 的单向性在这个模型下**不是缺陷，是刚好**。
3. **现有 REST 一行不用动** → 单人模式零回归风险（§7.5 有逐条对照）。

### 1.2 端点设计（新增，不动现有路由）

```
POST /api/pvp/match            # 入池 / 取消匹配 / 用房间码加入
POST /api/pvp/submit           # 提交本回合发言（幂等）
POST /api/pvp/typing           # typing 心跳（1s 节流，用于演出，非必要）
POST /api/pvp/report           # 举报
POST /api/pvp/resign           # 认输

GET  /api/pvp/events?rid=&seat=&last_seq=   # SSE 主信道（text/event-stream）
GET  /api/pvp/poll?rid=&seat=&since_seq=    # 降级：长轮询，返回同构事件数组
GET  /api/pvp/snapshot?rid=&seat=           # 重连：全量状态快照
```

**关键设计：SSE 与轮询返回完全相同的 `EventEnvelope`**，前端只换 transport，解析逻辑零改动。降级成本趋近于 0。

```jsonc
// EventEnvelope —— 两种 transport 共用
{
  "seq": 42,                    // 房间内单调自增，重连游标
  "type": "turn_resolved",      // 事件类型
  "ts": 1757000000.123,         // 服务端 monotonic 打的时间戳
  "payload": { /* 事件体 */ }
}
```

事件类型清单：`room_matched` / `turn_started` / `judging_started` / `turn_resolved` / `opponent_typing` / `heartbeat`（1s，带 `server_now` + `deadline_ms`）/ `safety_masked` / `room_paused` / `match_ended`。

### 1.3 降级策略（必须做）

企业代理、部分手机浏览器、微信内置浏览器会缓冲或掐断 SSE。**不能假设 SSE 一定可用。**

```
1. 前端建 EventSource
2. 3s 内未收到首个 heartbeat → 判定 SSE 不可用 → 切轮询（2s 间隔 /api/pvp/poll?since_seq=）
3. 运行中断流 → EventSource 自动重连（原生行为）+ 我们自己带 last_seq 回放
4. 连续 3 次重连失败 → 持久降级到轮询，本局不再尝试 SSE
```

服务端同时保留两条通道，无需协商 —— 轮询端点本来就是「SSE 的快照版」，实现成本几乎为零（共用同一个 `room.events` 环形缓冲）。

### 1.4 单机并发容量估算（2核2G，给算式）

**假设（全部标注，可推翻）**：

| 变量 | 取值 | 依据 |
|---|---|---|
| A1 可用内存 | **1.5 GB** | 总 2GB − OS/Python 解释器/静态数据 ≈ 0.4~0.5GB `[待实测]` |
| A2 每 SSE 连接 RSS | **~100 KB** | CPython 线程栈实际触碰 16~64KB + socket 收发缓冲 + 请求对象 |
| A3 CPython 舒适线程上限 | **600~800** | 超过后 GIL 争抢导致延迟抖动（经验值，`[待实测]`） |
| A4 每房间常驻连接 | **2**（双方各 1 条 SSE） | — |
| A5 保留给 POST 的线程 | **100** | 峰值短连接 |
| A6 回合周期 | **36.5 s** = 判定 1.5s + 玩家打字 35s（中位） | 真人打字 20~60s |
| A7 判定 in-flight = 房间数 × 判定耗时 / 回合周期 | — | Little's Law |
| A8 上游 LLM 并发上限 | **32** | `[待实测]`，各家 RPM/并发限额未核实（llm-selection §7.2 #4） |

**推导**：

```
【天花板 1 · 内存】  1.5GB / 100KB                 = 15,000 连接   → 不是瓶颈
【天花板 2 · 线程】  (700 − 100 POST) / 2 连接每房间 = 300 房间      → ★ 真瓶颈
【校验 · LLM 并发】  300 × 1.5s / 36.5s            = 12.3 in-flight < 32 ✅ 不构成瓶颈
【校验 · CPU】       700 连接 × 1 heartbeat/s       = 700 wakeup/s  → 2 核无压力
                     （判定是 IO 等待，本机不烧 CPU）
```

**结论：2核2G 单机稳态容量 ≈ 250~350 个进行中房间（500~700 同时在线玩家）。**

换算 DAU（按峰值并发 ≈ DAU × 5%~10%）：**单机可支撑约 7,000~14,000 DAU 的峰值在线**。`[待实测]`

**突破路径（M2 之后可选）**：把 SSE 从「每连接一线程」改为 `selectors` 单线程事件循环 + 队列广播 → 可到数千连接，但需重写 HTTP 层（违反不重写原则）→ **折中：M2 先上 threading 版本，设告警「线程数 > 600 持续 5 分钟」触发改造评估。**

**压测方法（M2 验收必做）**：`demo/tools/pvp_load.py` 起 N 个协程模拟房间，`llm_mode=mock` 下压线程数与内存，记录 P95 延迟拐点；再切真实 LLM 压上游并发。

### 1.5 房间/匹配服务进程内设计

```python
rooms: dict[rid, Room]        # 与现有 sessions 完全隔离（不动 sessions）
  Room = {
    rid, mode, topic, seats: {A: {uid, seat_token, elo, conn?}, B: {...}},
    turn_seq: int,            # 单调自增，乐观锁核心
    expected_side: "A"|"B",
    deadline_ms: int,         # monotonic 绝对截止
    conf: {"A": 100, "B": 100},
    token: {"A": 420, "B": 420},
    events: deque(maxlen=512),# 环形缓冲，重连回放
    _lock: threading.RLock(), # 沿用现有 session 锁模式，零新概念
  }

queue: dict[mode, list]       # 匹配池，进程内内存（O(n log n)，n<1000 完全够）
                              # DB 只做 30s 一次的崩溃恢复快照
```

**并发模型**：每 Room 一把 `RLock`（与现有 `state["_session_lock"]` 同构），**锁持有期只包含纯内存操作（<1ms），绝不包含任何 LLM 调用**。LLM 调用在锁外执行，结果通过 `apply_turn()` 重新取锁提交。这是与现有 `_process_message` 最大的差别，也是 PvP 能撑住并发的关键。

## 2. Q2 · 状态权威与一致性

### 2.1 服务端权威状态机

沿用 ADR-002 的核心原则（**状态由确定性代码唯一持有，LLM 只读**），PvP 下扩展为：

| 状态 | 持有者 | LLM 权限 |
|---|---|---|
| `turn_seq` / `expected_side` / `deadline_ms` | Room（服务端唯一） | 不可见 |
| 双方自信度 / token / 六维 / 漂移 | Room（服务端唯一） | 只读注入 |
| 判定结果 / 攻防标签 | Judge 产出 → `settle()` 消费 | 产出 |
| 对局历史 | Room + `turn` 表 | 只读注入（近 3 回合） |

**状态机**：`MATCHING → ONGOING（A_SPEAKING ⇄ B_SPEAKING）→ ENDED`
结束态：`A_WIN` / `B_WIN` / `ABANDON` / `TIMEOUT` / `RESIGN` / `FORFEIT_CIVILITY`（文明度归零判负）

### 2.2 回合锁（防双发）—— 乐观锁，不是长事务锁

```
submit(rid, uid, seat_token, turn_seq, client_msg_id, text):
    with room._lock:                                  # 持有期 <1ms
        if room.turn_seq != turn_seq:       → 409 {error:"stale_turn", current: room.turn_seq}
        if seat_of(uid) != room.expected_side: → 409 {error:"not_your_turn"}
        if room.last_msg_id == client_msg_id: → 200 返回缓存的上一响应（真幂等）
        # 通过：立即推进 turn_seq，标记 in-flight，释放锁
        room.turn_seq += 1; room.last_msg_id = client_msg_id
    # —— 锁外 ——
    judge → settle → 审核 → 广播
    with room._lock: apply_turn(...)                  # 再次取锁提交，<1ms
```

**为什么不用悲观锁**：现有 `_process_message` (L1420) 的模式是「持锁跑完 2 次 LLM」，单人下 2~4s 尚可（一个会话同时只有一个玩家）。PvP 下两个玩家并发 + 房间数上百 → 锁竞争直接雪崩。**乐观锁把临界区压到纯内存操作，是唯一可行的做法。**

### 2.3 幂等（同一回合重复提交）

三层保障，缺一不可：

| 层 | 机制 | 防的场景 |
|---|---|---|
| **L1 · 幂等键** | `client_msg_id`（客户端 UUID4），服务端记 `last_msg_id`，同 id 重放 → 返回缓存响应，**不重复扣 token** | 前端重试、网络重发、用户连点 |
| **L2 · 乐观锁** | `turn_seq` 必须严格相等，否则 409 | 双端同时提交、时序错乱 |
| **L3 · 席位校验** | `seat_token` + `expected_side` | 越权代打、伪造请求 |

> **这一条是 PvP 最容易引发真人纠纷的地方**：网络抖动导致前端重试，服务端扣了两次 token → 玩家会认为「系统黑我的口舌」。**L1 必须做，且是验收硬指标**（§7 M1b 验收④）。

### 2.4 超时 / 掉线 / 重连

**时限一律服务端判定，客户端计时器纯渲染（ADR-009）。**

- 服务端：`deadline_ms` 存 **monotonic 绝对时间戳**（`time.monotonic()`），由 1s 一次 `heartbeat` 事件下发 `{server_now, deadline_ms}`。
- ⚠️ **顺带修一个现有缺陷**：`server.py` L1346 `state["start_time"] = time.time()` 用墙钟，NTP 校时会跳。迁移到 `monotonic`。（改动见 §7.4 #6）

**分级处置**：

| 场景 | 阈值 | 处置 |
|---|---|---|
| SSE 短暂断流 | < 5s | `EventSource` 原生重连 + `last_seq` 回放，玩家无感 |
| 玩家掉线 | **30s 内重连** | 凭 `rid + seat_token` 回原房间；补发 `snapshot` + `seq > last_seq` 的增量事件；**回合计时继续走但给 30s 宽限** |
| 超时未提交 | 超过 `deadline_ms` | 该回合判**弃权**：对手气势条 +8（等同 L2 打强项的反向收益），自己 token 不扣 |
| 掉线超时 | **> 30s 未重连** | 判该回合弃权 |
| 连续弃权 | **连续 2 回合** | 判负 `LOSE_ABANDON`，对手 `WIN` |
| 双方都掉线 | 60s | 判和局，双方 Elo 不变 |

**为什么不是「一断线就判负」**：国内玩家大量在地铁/电梯/弱网环境玩，一断线就判负会把留存打穿。**30s 宽限 + 连续 2 回合才判负**是留存与公平的平衡点。这个阈值应做成配置（`pvp.abandon_grace_s` / `pvp.abandon_strikes`），上线后按数据调。

**重连状态重建**：`snapshot`（完整可公开视图）+ `since_seq` 增量事件回放。不用「纯事件重放」—— 房间事件缓冲只有 512 条，且新人观战/长时间掉线会溢出。

### 2.5 对局日志与可回放

每回合落一条 `turn` 记录（见 §6 表结构），含 `text` 原文 + `text_hash` + `judge` + `settlement` + `safety` + `input_feat`。

**回放不需要重跑 LLM** —— 这是 ADR-002（状态迁移只走纯函数）的巨大红利：
```
replay(rid) = 按 seq 重放 turn 记录 → 依次调用 settle() → 完全复现对局
```
- ✅ 判定结果、气势条变化、token 消耗：**可复现**（纯函数）
- ❌ NPC 台词：PvP 里没有 NPC，但**对手的发言是 LLM 之外的真人产物，必须存原文**，不能重生成。
- 回放大对象落 `data/replays/<rid>.json`，DB 只存路径。

## 3. Q3 · LLM 编排、延迟与成本（重点）

### 3.1 PvP 下每回合的调用变化

| 调用 | 单人 | PvP | 说明 |
|---|---|---|---|
| 判定 Judge | 1 | **1** | 只判当前发言方 |
| NPC 回复 | 1 | **0** | 🔴 **整个消失**——对手是真人 |
| 内容安全（云端机审） | 0~1 | **0~1（旁路）** | 灰区才调 |
| 局终复盘 | 1 | 0~1（可选） | 建议 PvP 只做规则模板版 |
| 局终记忆 | 1 | **0** | 无 NPC，无记忆 |
| **合计/回合** | **2~3** | **1（+ 旁路 0~1）** | **≈ 单人 1/3** |

**关键决策：不引入第 2 次判定。** 直觉上「双方各判一次」更公平，但：
- 判定的职责是「评估这条发言的质量」，不是「比较两条发言」。比较由 `settle()` 的确定性加减完成（ADR-002）。
- 加第二次判定 = 成本翻倍 + 延迟翻倍 + 引入了「两个裁判口径不一致」的新问题。
- **否决**。

**可选加分项（列为「可以不做」）**：AI 观战解说 / 裁判点评 → +1 次/回合，成本翻倍，且 PvP 的乐趣是「人怼人」，AI 插嘴是减分项。**明确不建议**。

### 3.2 延迟预算分解

**关键洞察：PvP 有两个完全不同的 SLA，必须分开定。**

| SLA | 定义 | 目标 | 理由 |
|---|---|---|---|
| **SLA-1** | 我提交 → 我看到自己的判定反馈 | **P95 ≤ 1.8s** | 超过 2s 会感觉"卡" |
| **SLA-2** | 对手提交 → 我收到对手文本 | **P95 ≤ 300ms** | 纯本机广播，必须极快 |
| — | 对手「什么时候提交」 | **无 SLA** | 由对手打字速度决定（20~60s），玩家有心理预期 |

| 环节 | 耗时 | 说明 |
|---|---|---|
| 提交 → 服务端收到 | ~50ms | 含公网 RTT |
| 本地前置审核（词表 + 正则） | **< 5ms** | 纯内存 |
| **判定 LLM（关键路径）** | **P95 1.5s** | 输入 760 token / 输出 41 token，沿用 ADR-005 非流式 |
| `settle()` + `schedule_pvp()` | < 10ms | 纯函数 |
| SSE 广播到双方 | < 50ms | 本机 |
| **SLA-1 端到端** | **P95 ≈ 1.65s** | ✅ 达标 |
| 云端机审（旁路异步） | 200~500ms | 🔴 **不在关键路径上**，见 §5.2 |

**判定 prompt 增量**：PvP 判定需要额外注入「对手上一轮原话 + 双方立场 + 双方气势差」→ 输入 644 → **约 760 token**（+120，保守）`[待实测]`。

**为什么 PvP 的延迟预算比单人宽松**：单人里 NPC 台词是玩家等待的终点（ADR-005 需要用演出掩盖）；PvP 里玩家等的是**对手的回复**，而对手是人——打字 20~60s，1.8s 的判定延迟完全被淹没。**这是 PvP 相对单人的结构性优势。**

### 3.3 单局 LLM token 成本 —— 公式 + 量级

**先定单局回合数**（按现有 token 经济推算，任务要求的 L1 420 / L5 280 口径）：
```
游戏内 token 消耗/回合 = TOKEN_BASE(20) + max(0, 字数 − TOKEN_FREE(60)) × 1
玩家平均 40 字/回合 → 每回合 20 token
L1 配额 420 → 420/20 = 21 回合 → 撞 MAX_TURN(20) → 20 回合
L5 配额 280 → 280/20 = 14 回合
→ 现有单人单局区间 14~20 回合

PvP 建议：双方各 8 回合 = N = 16 个发言（对称、公平、8~10 分钟，适配移动端碎片时间）
下方按 N = 12 / 16 / 20 三档给数（N = 双方发言总数）
```

**成本公式**：

```
C_pvp(N) = C_judge(N) + C_mod(N) + C_retro

C_judge(N) = N × [ J_in × (1−h) × P_in  +  J_in × h × P_cache  +  J_out × P_out ] / 1e6
C_mod(N)   = N × r_gray × P_mod
C_retro    = 0.0013 元（可选，局终复盘 1 次）或 0（规则模板版）

参数（全部标注来源与假设）：
  J_in   = 760  token   判定输入 = 单人实测 644 + PvP 增量 ~120  [待实测]
  J_out  = 41   token   判定输出（schema 不变，llm-selection §1.2 实测）
  h      = 0.61         缓存命中率 = 静态前缀占比 0.68 × 命中率 0.90（同 §1.2 口径）[待实测]
  P_in/P_out/P_cache = 0.8 / 2.8 / 0.23 元每百万（GLM-5.3-Flash，llm-selection §2.1）
  r_gray = 0.45         云端机审调用率（灰区率）。单人取 0.30，PvP 上调到 0.45
                        —— 理由：人对人攻击性显著强于人对 NPC，灰区比例更高
  P_mod  = 0.0022 元/条（天御 22 元/万条，release-plan §2.6 已核实）
```

**量级数字（元/局）**：

| N（单局发言数） | 判定 LLM（无缓存） | 判定 LLM（缓存 61%） | 内容安全（灰区 45%） | 复盘（可选） | **合计（无缓存）** | **合计（缓存）** |
|---:|---:|---:|---:|---:|---:|---:|
| 12 | 0.0087 | 0.0055 | 0.0119 | 0.0013 | **0.0219** | **0.0187** |
| **16（推荐）** | 0.0116 | 0.0073 | 0.0158 | 0.0013 | **0.0288** | **0.0245** |
| 20 | 0.0145 | 0.0092 | 0.0198 | 0.0013 | **0.0356** | **0.0303** |
| 悲观档 N=16（全量机审、无缓存） | 0.0116 | — | 0.0352 | 0.0013 | **0.0481** | — |

**横向对比（N=12，与单人同口径）**：

| 项 | 单人（12 回合） | **PvP（12 发言）** | 倍数 |
|---|---:|---:|---:|
| LLM | 0.032（缓存后 0.021） | **0.0087（缓存后 0.0055）** | **27%** |
| 内容安全 | 0.0079（灰区 30%） | **0.0119（灰区 45%）** | **151%** |
| 局终附加 | 0.0028 | 0.0013（复盘）/ 0 | 46% |
| **合计** | **0.040（无缓存）/ 0.031（缓存）** | **0.0219 / 0.0187** | **≈ 55%** |

> **两条必须说清的结论**：
> ① **PvP 的 LLM 成本只有单人的 27%** —— NPC 生成（1,545 in + 67 out/回合，占单人成本 68%）整个消失。
> ② **但内容安全成本反超 51%** —— 双向 UGC + 人对人攻击性更强 → 灰区率从 30% 上调到 45%。
> 两相抵消后 **PvP ≈ 单人的 55%，约 2.2 分/局**。**不是"便宜一个数量级"，是"便宜一半"。**

**DAU 账（N=16，3 局/天，30 天）**：
```
1 DAU 月成本   = 90 局 × 0.0245~0.0288 = 2.21 ~ 2.59 元
1,000 DAU/月   = 2,210 ~ 2,590 元
10,000 DAU/月  = 22,100 ~ 25,900 元
（对照：单人 1,000 DAU = 2,889 元 LLM-only / ~4,050 元含审核 —— release-plan §3.1）
```

### 3.4 并发排队 / 限流 / 超时降级

**限流三级**（沿用 llm-selection §3.1 的三层结构，按 PvP 调整）：

| 级 | 阈值 | 说明 |
|---|---|---|
| 全局 LLM in-flight | **32**（信号量）+ FIFO 队列上限 64 | `[待实测]`，受上游并发限制 |
| 每 uid | 10 局/天、60 req/min | 沿用 |
| 每 IP/24 | 30 局/天 | 沿用 |
| 每房间 | 1 turn in-flight | 回合锁天然保证 |

**超时降级触发条件（明确，不做模糊表述）**：

| 条件 | 动作 | 理由 |
|---|---|---|
| 判定 **> 3s**（软超时） | 中止调用，标记 `degraded` → **该回合不计、不扣 token、允许玩家重发** | 🔴 **PvP 降级必须是「无损重试」** |
| 判定 **> 8s**（硬超时） | 同上 + `degrade_count += 1` | 沿用 llm-selection §5.1 #4 |
| 单房间连续 3 次降级 | 房间暂停，推 `room_paused`，30s 后自动恢复 | 防止玩家在坏房间里一直重试 |
| 全局降级率 > 5%（5min 滑窗） | P1 告警 + 自动切备用供应商 | 沿用 ADR-006 D4 |
| 全局降级率 > 20% | **自动关闭 PvP 匹配入口**（已开房间允许打完） | 止损 |
| 全局日消费 > 阈值 | 熔断：新对局需看激励视频 / 次日再来 | 沿用 |

> 🔴 **PvP 的降级与单人有本质区别**：单人降级到 `_mock_judge` 关键词表，玩家顶多觉得"判定玄学"；**PvP 降级误判会直接影响另一个真人的胜负，必然引发纠纷**。所以 PvP 的降级不能是「糊弄过去」，必须是 **「无损重试」**——不计、不扣、可重发。这一条写进 ADR-010。
>
> 同时重申 llm-selection §5.1 #13：三级降级链（主 → 备用便宜模型 → 规则兜底）**必须在 PvP 上线前做完**，不能再是 `llm → mock 关键词表` 的断崖。

### 3.5 用演出掩盖延迟（ADR-005 的 PvP 版）

单人里演出掩盖的是「NPC 生成」；PvP 里要掩盖的是「判定」，对象变了。

| 时序 | 事件 | 前端表现 | 延迟 |
|---|---|---|---|
| T0 | 玩家点发送 | 本地回声 + "已送达" | 0ms |
| T1 | 服务端收到，推 `judging_started` | "裁判正在看…" + 气势条抖动 | ~10ms |
| T2 | 判定完成，推 `turn_resolved` | 气势条变化 + **攻防标签 VFX**（复用现有异议闪屏通道） | ~1.5s |
| T3 | 推给对手 | 对手端"轮到你了" | ~50ms |
| T4 | 对手开始打字，推 `opponent_typing`（1s 节流） | "对方正在组织语言…" | 真实信号 |
| T5 | 对手提交 | 文本到达 | 由人决定 |

**关键：T1 和 T4 是真实事件、零成本，且把 1.5s 的判定延迟完全填满。**
`opponent_typing` 是 PvP 最好的延迟掩盖手段 —— 它真实、免费、且让玩家感觉"对面是个活人"。

**另一个零成本手段**：判定与云端机审**并行**而非串行（§5.2）。本地前置 <5ms 后立即发起判定，机审旁路走，200~500ms 完全不进关键路径。

## 4. Q4 · 反作弊

### 4.1 AI 代打检测 —— 先说结论

> 🔴 **AI 代打无法被可靠检测。** 下面所有手段都是「提高作弊成本」，没有一条能「阻断」。
> **真正的解药在玩法设计，不在检测技术。**（§4.2 是给设计侧的头号建议）

| 手段 | 能做？ | 强度 | 成本 | 说明 |
|---|:---:|:---:|---|---|
| **粘贴检测** | 部分 | 弱 | 0.2 人日 | 前端监听 `paste` + `oninput`：<100ms 内长度 +200 字 → `paste_suspected`。**极易绕过**（浏览器扩展 / CDP / 手动打字）。定位为弱信号，不单独定罪 |
| **输入节奏 / 流式特征** | ✅ | 中 | 0.5 人日 | 采集聚合特征：按键间隔均值/方差、长度-时间曲线、退格率。真人 = 长尾分布 + 有退格 + 阶梯增长；LLM 粘贴 = 单次跳变 + 方差≈0 + 退格率≈0。用**阈值打分卡**，不用 ML（没训练数据，2核2G 也跑不动） |
| **文本困惑度 PPL** | ❌ **不能** | — | — | **明确否决**：① 本地跑不动（需语言模型，2核2G 无 GPU）；② 云端 API 无 PPL 接口；③ 现代模型上中文 PPL 对「AI 味」判别力已很差。**别在这上面浪费时间** |
| **统计指纹（LLM 味）** | ✅ | 弱-中 | 0.5 人日 | 结构化程度过高（"第一…第二…综上所述"）、连接词密度高、几乎无错别字/口语填充词、长度稳定在 200~400 字。真人对抗特征：短句、口语、有错别字、长度波动大。打分卡 |
| **长度突变** | ✅ | 弱 | 0.1 人日 | 前 5 回合均值 40 字 → 突然 380 字 |
| **上下文贴合度 `relevance`** | ✅✅ | **强** | **≈0** | 🔴 **本项目独有的杀招，见下** |

**`relevance` —— 零增量成本的强信号（重点推荐）**：

外部 LLM 拿到的只有「题目」，拿不到「本局对话历史 + 对手上一轮原话 + 对方立场」。所以代打回复**常常不接对手的话**，或**带出题目里没出现的背景**。

工程化方式：**在现有单次判定调用的 schema 里加一个字段**，不新增任何 LLM 调用：

```jsonc
{
  "dimension": "EVIDENCE",
  "strength": "L2",
  "confidence": 0.82,
  "relevance_to_last": 0.35,   // ← 新增：本条发言对「对手上一轮」的直接回应度 0~1
  "safety": { "level": 0, "tags": [] }
}
```

- **成本 = 0**（同一份 prompt、同一次调用，多输出几个 token ≈ +0.00002 元/回合）
- 用法：`relevance_to_last < 0.3` 且连续 2 回合 → 打可疑分
- 更进一步（设计侧）：**把 `relevance` 做成硬规则** —— `relevance < 阈值` 直接判 L0。代打者就必须把对手原话也粘给外部 LLM，操作成本陡增。

### 4.2 给设计侧的头号建议：反代打的战场在玩法设计

| 机制 | 效果 | 成本 |
|---|---|---|
| 🔴 **限时（每回合 45~60s，服务端计时）** | **最强**。代打需要切窗口 + 复制题目 + 等生成 + 复制回来 + 粘贴，**45s 内做不完 4 步**。 | **0** |
| 🔴 **强制回应对手原话** | 次强。代打者必须把对手原话一起喂给外部 LLM，且要理解上下文。复用 `relevance` 字段做硬规则。 | **≈0** |
| 🟡 **追问链**（连续 2 回合必须围绕同一论点深入） | 外部 LLM 一次性生成的长文会显得脱节 | 低 |
| 🟡 **赛后即时追问**（局终随机抽一回合问"你当时为什么这么说"） | 代打者答不上来。但增加摩擦，可能伤留存 | 中 |

> **一句话给文策渊**：检测是猫鼠游戏，永远落后一步；**限时才是对 AI 代打的降维打击** —— 它攻击的是代打的**操作时间成本**，而不是**文本特征**。

### 4.3 复读 / 模板刷分 / 切题 / 刷屏

| 问题 | 手段 | 能做？ | 实现 |
|---|:---:|---|---|
| 复读 | **simhash / 3-gram Jaccard** vs 本局历史 + 跨局历史（同 uid） | ✅ 强 | stdlib 可实现，无需第三方。阈值 > 0.85 → 判 L0 |
| 模板刷分 | `hit_stats` 维度分布检测：连续 3 回合命中同维度且文本高度相似 | ✅ | 复用现有 `hit_stats`（L1367） |
| 切题 | Judge 已有 `NULL` 维度（离题）；补一层字符级 n-gram 与 `topic` 关键词 + 对手上一轮的重叠度 | ✅ | 无需 embedding |
| 刷屏 | **现有 token 经济已经是反刷屏机制，不用另建** | ✅ | `TOKEN_FREE=60` 之后 1 token/字，300 字发言消耗 260+ token（配额 420 只够 1.5 次）。长文天然被惩罚 |
| 提交频率 | 同 uid 5s 内 >1 次提交 → 拒绝 | ✅ | 令牌桶 |

### 4.4 多开 / 小号互刷 / 匹配操纵

| 手段 | 能做？ | 说明 |
|---|:---:|---|
| 同设备指纹识别 | ✅ | `device_fp = hash(ua + screen + tz + canvas 简易指纹 + salt)`，**不存原文** |
| 同 IP/24 识别 | ✅ | `ip_h24 = hash(ip/24 + salt)`，**不存原文 IP**（个保法要求） |
| **禁止互配** | ✅ **最强** | 同 `device_fp` 或同 `ip_h24` 的两人**永不匹配到同一局** → 直接掐死双开自刷 |
| Elo 异常检测 | ✅ | 两人间胜负严重偏离期望 + 对局时长过短 + 发言质量分异常 → 标记 |
| 识别真实小号 | ❌ **不能** | 不同设备、不同网络 → 无解 |
| 指定对手 / 房间码刷分 | ✅ | **房间码只用于友谊赛，友谊赛不计 Elo**；排位只能随机匹配 |

**「有效对局」闸门**（缓解小号刷分，最实用）：
```
elo_applied = 1 需同时满足：
  ① 对局 ≥ 6 回合（N ≥ 12 发言）
  ② 双方平均发言 ≥ 30 字
  ③ 非同 device_fp / 非同 ip_h24
  ④ 双方均未触发 L0 连击（l0_streak < 2）
  ⑤ 双方 shadow_score < 30
不满足 → 记战绩、留回放，但 Elo 不变动
```

### 4.5 客户端计时器篡改

**能做，且是必须做（ADR-009）**：
- 所有时限服务端：`deadline_ms` 存 Room，用 `time.monotonic()` 判定（不受系统时间/NTP 影响）
- 前端每秒收 `heartbeat{server_now, deadline_ms}`，**只用于渲染**
- 前端倒计时与服务端 `deadline_ms` 偏差 > 3s → 以前端显示为准重绘，并把偏差上报（可反推客户端篡改）

### 4.6 处置策略：影子池，不封禁

**不做自动封禁** —— 误伤代价高（真人流失），且没有申诉人力。

```
shadow_score 累积（各项检测加权）：
  0~30   正常
  30~60  标记：对局不计 Elo
  60~80  降权 + 只进影子池
  80+    影子池 + 人工复核队列
```

> 🔴 **影子池（shadow pool）是最好的处置**：不作声、不告知，把可疑玩家**只匹配给同样可疑的玩家**。
> - 对真人：**零误伤**（他永远有对手、永远能玩，只是"对手也怪怪的"）
> - 对作弊者：**最大惩罚**（他们互相刷，数据污染被隔离在影子池里，不污染主池 Elo）
> - 对运营：**零人力**（不需要申诉复核）
>
> 这是我在这个体量下能想到的最高性价比处置，强烈推荐。

### 4.7 诚实清单：能真做 vs 做不了

| ✅ 能真做 | ❌ 做不了 / 不建议做 |
|---|---|
| 服务端计时（强） | 困惑度 PPL（本机动不了，云端无接口） |
| `relevance_to_last` 上下文贴合度（强，零成本） | 可靠阻断 AI 代打（无解，只能提高成本） |
| 复读/模板检测 simhash（强） | 识别真实小号（不同设备无解） |
| 限时赛制（**最强，成本 0**） | 实时人工审核（单人团队无 7×24） |
| 同指纹/IP 禁止互配（强） | 客户端完整性校验（无前端加固，浏览器环境不可信） |
| 输入节奏聚合特征（中） | 行为生物特征（逐键时间戳 → 个保法敏感信息，**禁止采集**） |
| 统计指纹打分卡（弱-中） | — |
| 影子池软处置（强，零误伤） | — |

> ⚠️ **合规红线（易被忽略）**：输入节奏检测**只能上报聚合特征**（均值/方差/最大跳变/退格率/总耗时），**绝不能留逐键击键时间戳** —— 那是行为生物特征，属《个保法》敏感个人信息，会触发一整套额外义务。见 §5.5。

## 5. Q5 · 内容安全（最高风险项，重点展开）

> **PvP 把这个项目的 UGC 风险放大一个数量级**：单人模式里玩家的输入只喂给 LLM 和裁判；PvP 里**玩家的原文会直接出现在另一个真人的屏幕上**，且带有「我对你在对喷」的动机。
> 但同时，PvP 有一个**降低风险的结构性优势**：**1v1 私密房间的受众只有 1 个人**，不是公开广场。这个区别决定了审核链路可以异步（§5.2）。

### 5.1 三层审核链路

```
玩家提交 text
  │
  ├─ [T0 · <5ms] L1 本地前置（同步，关键路径）
  │     敏感词 + 变体（拼音 / 谐音 / 繁简 / 符号分隔 / 全半角）
  │     + 长度上限 + 纯符号检测 + 刷屏重复字符检测
  │     命中 BLOCK 级 → 立即拒答 + 违规计次 + 友好提示
  │     命中 MASK 级  → 打码后继续走判定，但结果强制降 L0（§5.3 约束①）
  │
  ├─ [T1 · P95 1.5s] 判定 LLM（同步，关键路径）
  │     schema 扩展 safety: {level, tags}
  │     （与 L1 并行：L1 通过后立刻发起，不等云端机审）
  │
  ├─ [T2 · 旁路异步] L2 云端机审（腾讯云天御 TMS）
  │     只对「灰区」调用：L1 未命中高危 且 文本特征可疑
  │     （中风险词命中 / 长度异常 / relevance 异常 / 该 uid 有前科）
  │     结果异步回填 → 命中则事后处置（追加违规计次 / 撤回放回 / 影子池 / 封禁）
  │
  └─ [T3 · 输出侧] 本地回扫（同步，<5ms）
        对「将下发到对手的原文」做关键词回扫
        命中 → 打码替换后再推给对手（对手端看到 ██）
```

### 5.2 🔴 关键决策：云端机审必须旁路异步，不能串在关键路径

| 方案 | 端到端延迟 | 风险 | 结论 |
|---|---|---|---|
| 同步前置机审 | P95 1.8s → **2.3s+** | 审核服务抖动 → 整个对局卡死 | ❌ |
| **旁路异步** | **P95 1.65s（不变）** | 最多 1 条违规内容短暂可见（<1s） | ✅ |

**为什么这个代价可接受**：PvP 是 **1v1 私密房间**，受众只有对手 1 人，不是公开聊天室/评论区。违规内容的传播面被物理限制在 1 人 × 1 次。

> 🔴 **但这是形态的分叉点，必须写死**：
> - **1v1 私密对局** → 旁路异步 ✅
> - **公开观战 / 公开展厅 / 弹幕 / 世界频道** → **必须同步前置审核**，因为受众是 N 人且可被截图传播
> - **M0~M2 绝不做公开观战**（见 §5.5 红线 #3）

### 5.3 「打码」能否做成游戏机制 —— 给设计侧的建议

**结论：可以做，而且应该做。这是本项目少数能把合规成本转化为玩法资产的机会。但必须满足三条硬约束。**

**正面建议（给文策渊）**：

| 机制 | 说明 | 成本 |
|---|---|---|
| 🟢 **「文明度」第三条资源条** | 每局一条 0~100 的文明度。命中违规 → 扣文明度 + 词被打码 + **对手气势条反涨**（"你急了"）。文明度归零 → 判负 `FORFEIT_CIVILITY`（"你被判罚出场"）。→ 与现有气势条 / token 条三足鼎立，**把审核惩罚变成可玩的第二条资源** | 低（复用现有条 UI） |
| 🟢 **打码演出** | 命中的词显示为 `██` + 一声"哔——"，对手端提示"对方说了句脏话" + 对手获得一次性反击加成。**复用现有异议闪屏的 VFX 通道，零新增美术** | **≈0** |
| 🟡 **「嘴臭流」玩法分支** | 允许玩家**故意**用打码换气势（骂人涨自己气势但掉文明度），形成风险/收益权衡 | 中 |
| ❌ **但不建议做** | 它会**激励违规内容**——监管视角下这是重大过失。列为「可以不做」 | — |

**三条硬约束（必须写进设计文档）**：

> **① 违规必须永远净亏。**
> 打码是**处置手段**，不能变成"骂人的安全出口"。如果玩家发现"骂人只是变星号还能涨气势"，我们就是在**激励违规**。
> 强制：**打码后该发言仍判 L0（无效发言）+ 扣文明度 + 文明度归零判负**。让违规永远净亏，机制才站得住。
>
> **② 词表是敏感资产，绝不下发前端。**
> 词表只在服务端。前端只接收 `{hit: bool, masked_text: str}`。**把词表打进前端 bundle = 发一本绕过手册给玩家。** 这条很多人会做错。
>
> **③ 绝不提供"还原"或"猜词"功能。**
> 那是帮用户绕过审核，直接踩内容安全红线（《暂行办法》第 14 条的反向适用）。

**附：词表分级（防误判，M0 就要定）**

| 级别 | 处置 | 内容 |
|---|---|---|
| `BLOCK` | 硬拦 + 拒答 + 违规计次 | 政治敏感 / 暴恐 / 色情 / 违禁品（**M0 只开这一级**） |
| `MASK` | 打码 + 判 L0 + 扣文明度 | 辱骂 / 人身攻击 / 歧视（辩论场景高频，**先只 MASK 不 BLOCK**） |
| `WARN` | 只记录不处置 | 语气词 / 方言 / 正常辩论用词（"杀""干掉""打脸""扯淡""废话"） |

> ⚠️ **误判是这个机制最大的产品风险**：辩论品类里"扯淡""放屁""你这是诡辩"是正常表达。一刀切 BLOCK 会让玩家玩不下去。**M0 阶段只开 BLOCK 的高危政治/色情/暴恐，辩论常见脏话先只 MASK 不 BLOCK**，用天御免费 3,000 条额度跑一遍真实语料测误判率再调。

### 5.4 举报 / 人工复核 / 证据留存

**举报**：`POST /api/pvp/report {rid, seq, reason}` → 落 `report` 表。

**证据留存（分层，两层满足不同义务）**：

| 层 | 内容 | 留存 | 说明 |
|---|---|---|---|
| **一般调用日志** | `text_hash` + 长度 + 命中标签 + 时间戳 | 6 个月 | 沿用 release-plan §2.7「原始输入脱敏」 |
| **`moderation_queue`（举报复核）** | **必须存原文** | 6 个月 + 到期自动删 | 加密存储 + 访问审计。⚠️ **与上面一条冲突，必须显式决策** |

> ⚠️ **冲突点（必须让主理人拍板）**：release-plan §2.7 建议「日志中对原始输入脱敏，仅存 hash + 长度 + 命中标签」；但 **PvP 的举报复核必须有原文才能定性**。
> **我的建议：分两层。** 一般调用日志脱敏；`moderation_queue` 存原文（加密 + 访问审计 + 6 个月 TTL + 到期自动删）。两层各满足不同义务，且访问面最小化。

**人工复流程（诚实版）**：
```
举报 → moderation_queue（pending）
     → 48h 内人工复核（自动受理回执 + 批量处理）
     → 处置：warn / shadow / ban / 回滚 Elo / dismiss
     → 通知举报人
```
> 🔴 **一个人做不了 7×24 实时人工复核。** 现实方案：**举报只做「标记 + 事后批量复核 + 高频举报者自动进影子池」**，不承诺实时处理。但**公示的响应时限必须写 ≤48h**（《暂行办法》第 15 条要求公布处理流程和反馈时限），用「自动受理回执 + 批量处理」满足形式要求。这一点要对主理人说清楚，不要自欺。

**🔴 一键熔断开关（M0 就要做，0.5 人日）**：
```
config.json:  { "pvp": { "kill_switch": "off" | "sync_moderation" | "closed" } }
  off              → 正常（旁路异步审核）
  sync_moderation  → 所有发言强制同步前置审核（发生事故时的紧绷模式）
  closed           → PvP 完全下线，只留单人模式
```
这是发生重大事故时**唯一的救命绳**。成本 0.5 人日，M0 阶段必须做，不能等到 M2。

### 5.5 合规清单与红线

**PvP 带来的合规变化（相对单人）**：

| 项 | 单人 | **PvP** | 依据 |
|---|---|---|---|
| 生成式 AI 登记 | 🟡 可能要 | 🔴 **确定要** | 「人对人交互」强化「舆论属性/社会动员能力」判定 → 《暂行办法》第 17 条算法备案 |
| release-plan 五要素自检 | 命中 ②③④（3 个） | 🔴 **命中 4 个**（④从"联网 session"升级为"人对人交互"，权重更高） | release-plan §2.2 |
| UGC 内容安全责任 | 单向（玩家→系统） | 🔴 **双向（玩家↔玩家）** | 《暂行办法》第 4/9/14/15 条；「技术中立」不构成抗辩 |
| 举报机制 | 🟡 | 🔴 **必须**（人对人场景举报率会高一个量级） | 第 15 条 |
| ICP 域名备案 | 路径 B/C 必办 | 同，**且 PvP 下无豁免空间** | release-plan §2.1 |
| 公安备案 | 备案号下发后 30 日内 | 同 | 同上 |
| 实名 | ❌ 不做 | ❌ **仍不做**（坚持零 PII） | 见下方取舍 |
| 未成年人限制 | 🟡 18+ 勾选 | 🔴 **必须加一条：不提供任何陌生人社交入口** | 见下方 |
| 日志留存 | 6 个月 | 6 个月（**+ 举报原文层**） | release-plan §2.7 |

**实名的取舍（必须让主理人拍板）**：
- **不做实名** → 无法有效封禁、无法防未成年人。
- **做实名** → 手机号/身份证是强 PII，义务陡增，且个人主体接不进国家统一实名认证系统（release-plan §2.5）。
- **我的建议：不实名 + 匿名 uid + 设备指纹 + 影子池**，接受"封禁不彻底"的代价。理由：本项目**没有付费资产**，封禁失效的代价可控；而收集实名的合规代价是确定的。

**未成年人的补偿性缓解（不做实名时）**：
1. 首启「面向 18 周岁以上」勾选确认
2. 题库 + prompt 护栏（禁止针对未成年人的诱导性内容）
3. 🔴 **PvP 不提供任何陌生人社交入口：无好友、无私聊、无自定义昵称** → 把"人对人"严格限制在"匿名对局内"。
   > **这一条价值极大**：砍掉好友/私聊/昵称 = 砍掉一大块《未保条例》下的社交风险，且**对核心玩法零损失**（辩论不需要好友系统）。**强烈建议写进设计约束。**

### 5.6 🔴 红线清单：什么不能做

| # | 红线 | 理由 |
|---|---|---|
| 1 | ❌ **不能有人对人自由文本聊天**（好友/私聊/世界频道/弹幕） | 那是社交产品，合规面爆炸，单人团队无法审核 |
| 2 | ❌ **不能有可自定义昵称** | 昵称是最容易出违规内容的 UGC 入口，且零玩法价值。用系统匿名代号（"红方"/"辩手 A"） |
| 3 | ❌ **不能有公开观战 / 公开房间**（M0~M2） | 除非同步前置审核 + 延迟播出 + 举报通道全上线 |
| 4 | ❌ **PvP 题库不能含政治 / 地缘 / 民族宗教 / 性别对立类命题** | AI 辩论里这些是"高热度"题，但 PvP 下两个真人会真的吵起来并留下证据。**题库白名单制**：只开放生活 / 消费 / 职场 / 教育 / 科技类 |
| 5 | ❌ **不能把违规原文或词表下发到前端** | 发词表 = 发绕过手册 |
| 6 | ❌ **不能提供"还原打码"或"猜词"功能** | 帮用户绕过审核 |
| 7 | ❌ **不能用境外 LLM** | 合规红线（llm-selection §2.4）。PvP 额外风险：判定 prompt 含玩家 UGC → **数据出境** |
| 8 | ❌ **不能留存逐键击键时间戳** | 行为生物特征 = 个保法敏感个人信息。只留聚合特征 |
| 9 | ❌ **不能在完成生成式 AI 登记前上线 PvP 公开匹配** | CAC 2026 清朗专项头号整治项，已处置 AI 产品 1.4 万余款 |
| 10 | ❌ **不能让违规"净收益"** | 任何打码/演出机制下，违规方的判定结果必须劣于不违规（§5.3 约束①） |
| 11 | ❌ **不能在未备案域名 / 公网 IP:端口 上做公开 PvP 匹配** | ICP 备案是硬前置；IP:端口 直连只可用于局域网/好友内测 |

## 6. Q6 · 数据层

### 6.1 选型：sqlite3 —— 是，且是唯一正确选择

| 维度 | 结论 |
|---|---|
| **是否够用** | ✅ **完全够用**，且是唯一符合硬约束的选择 |
| **理由** | ① `import sqlite3` **stdlib 自带，零依赖**（硬约束）；② 单机部署，WAL 模式写吞吐远超需求；③ 运维成本 0（无独立进程、无密码、备份 = 复制文件）；④ 从 JSON 迁移成本低 |
| **写量校验** | 每回合 1 条 `turn` + 每局 1 条 `match`。1,000 DAU × 3 局 × 16 回合 = 48,000 写/天 ≈ **0.56 写/s**（峰值按 10 倍 = 5.6 写/s）。**SQLite WAL 轻松支撑千级写 QPS，余量 3 个数量级。** |
| **不够的场景** | 多机部署（文件锁）、>1k 写/s、复杂分析查询 —— 本项目均不涉及 |
| **必须开的 PRAGMA** | `journal_mode=WAL`（读写不互斥）、`synchronous=NORMAL`（WAL 下安全且快）、`busy_timeout=5000` |
| 🔴 **必踩的坑** | 现有 `ThreadingHTTPServer` 是多线程 → **sqlite3 连接不能跨线程共享**（默认 `check_same_thread=True`）。**必须用 `threading.local()` 每线程一个连接。** 不写这条，implementer 一定会踩 |

### 6.2 表结构草案（最小集）

```sql
-- 1. 账号（最小可用：游客优先，零 PII）
CREATE TABLE account (
  uid          TEXT PRIMARY KEY,          -- 匿名 uid，服务端 uuid4
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER NOT NULL,
  device_fp    TEXT,                      -- hash(ua+screen+tz+salt)，不存原文
  ip_h24       TEXT,                      -- hash(ip/24+salt)，不存原文 IP
  status       TEXT NOT NULL DEFAULT 'active',   -- active|shadow|banned
  shadow_score INTEGER NOT NULL DEFAULT 0,       -- 反作弊打分卡累计
  elo          INTEGER NOT NULL DEFAULT 1200,
  games        INTEGER NOT NULL DEFAULT 0,
  wins         INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_account_fp ON account(device_fp);

-- 2. 对局
CREATE TABLE match (
  rid         TEXT PRIMARY KEY,
  mode        TEXT NOT NULL,              -- hotseat|indirect|pvp_async|pvp_sync
  topic_id    TEXT NOT NULL,
  a_uid TEXT, a_elo INTEGER,
  b_uid TEXT, b_elo INTEGER,
  result      TEXT,                       -- A_WIN|B_WIN|DRAW|ABANDON|RESIGN|FORFEIT_CIVILITY
  started_at  INTEGER, ended_at INTEGER,
  turn_count  INTEGER DEFAULT 0,
  elo_applied INTEGER NOT NULL DEFAULT 0, -- 0=不计分（可疑局/友谊赛/短局/影子局）
  replay_path TEXT                        -- 回放 JSON 落盘路径（大对象不进 DB）
);
CREATE INDEX idx_match_a ON match(a_uid, ended_at DESC);
CREATE INDEX idx_match_b ON match(b_uid, ended_at DESC);

-- 3. 回合（回放 + 审核证据 + 反作弊素材，三合一）
CREATE TABLE turn (
  rid      TEXT NOT NULL,
  seq      INTEGER NOT NULL,              -- 单调回合序号（乐观锁核心）
  side     TEXT NOT NULL,                 -- A|B
  uid      TEXT NOT NULL,
  text     TEXT NOT NULL,                 -- 原文（举报复核证据；加密 + 6个月TTL）
  text_hash TEXT NOT NULL,
  judge_dim TEXT, judge_strength TEXT, judge_conf REAL,
  delta_conf INTEGER, token_cost INTEGER,
  safety_lvl  INTEGER NOT NULL DEFAULT 0, -- 0=正常 1=打码 2=拦截
  safety_tags TEXT,                       -- JSON array
  relevance   REAL,                       -- 反代打信号：对上一轮的回应度
  input_feat  TEXT,                       -- JSON：聚合输入特征（禁存逐键时间戳）
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (rid, seq)
);

-- 4. 匹配池（常驻内存为主，DB 仅崩溃恢复，30s 快照一次）
CREATE TABLE queue (
  uid TEXT PRIMARY KEY, elo INTEGER NOT NULL,
  mode TEXT NOT NULL, enqueued_at INTEGER NOT NULL,
  device_fp TEXT, ip_h24 TEXT
);

-- 5. 举报与复核
CREATE TABLE report (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  rid TEXT NOT NULL, seq INTEGER NOT NULL,
  reporter_uid TEXT NOT NULL, reason TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',  -- pending|reviewed|dismissed|actioned
  action TEXT,                             -- warn|shadow|ban|none
  created_at INTEGER NOT NULL, resolved_at INTEGER, note TEXT
);
```

**🔴 明确不迁移（降低回归风险）**：

| 数据 | 现状 | 决策 |
|---|---|---|
| NPC 记忆 `npc_state.json` | JSON 文件 | **不迁**。避免动到单人模式热路径（`_finalize_match` L1541 / `_gen_memory`），迁移风险 > 收益 |
| 天梯进度 `progress.json` | JSON 文件 | **不迁**。同上 |
| 回放大对象 | — | 落 `data/replays/<rid>.json`，DB 只存路径 |

> 这条是刻意的**「不迁」决策**：SQLite 的价值在于「PvP 新增的关系型数据」，不是「替换现有 JSON」。少动一处就少一分回归风险。写进 ADR-012。

### 6.3 账号体系：无真实账号现状下的最小可用

| 阶段 | 方案 | 说明 |
|---|---|---|
| **M0 / M1** | **纯游客**：服务端签发 `uid = uuid4()`，写 `localStorage`，30 天轮换 | 🔴 **不收集任何个人信息**（沿用 release-plan §2.7 的零 PII 优势）。风险：清缓存/换设备 = 丢号 |
| **M2** | **微信授权（推荐）** | ① 国内玩家 100% 有微信；② 网页/小程序都能拿 openid；③ openid 是弱 PII，进隐私政策即可；④ 🔴 **天然给出设备级唯一性 → 直接解决多开/小号**（一个微信号 = 一个 uid）。**反作弊收益极大** |
| — | ❌ **不推荐手机号** | ① 需短信服务商（成本 + 资质）；② 手机号是强 PII，义务重；③ 个人主体接短信 SDK 麻烦；④ 转化漏斗掉一半 |

> **关键判断：没有付费资产 → 不需要强账号。** 我们现在只有 Elo 和战绩，丢号代价低。所以 M0/M1 用游客完全可接受，**把账号体系的复杂度推迟到真的有东西要保护时**（M2 / 路径 C）。

**必须配套**：个保法要求的**注销/删除渠道** → uid 设计必须保证所有表能按 uid 级联删除（`account` / `match` / `turn` / `queue` / `report` 都有 uid 或可 join）。

### 6.4 匹配池 / 战绩 / Elo / 回放

| 项 | 方案 |
|---|---|
| **匹配池** | **进程内内存**（有序列表，O(n log n)，n<1000 完全够）+ DB 30s 崩溃恢复快照。进 DB 是过度设计 |
| **匹配算法** | `Elo 差值 ≤ 200`，按等待时间放宽 `±(200 + 等待秒数 × 10)`，封顶 `±400`；**同 `device_fp` / 同 `ip_h24` 禁止互配** |
| **Elo** | 标准 Elo，K=32（新号前 10 局 K=64 快速收敛）。**只在 `elo_applied=1` 的有效局上计算**（§4.4 五条闸门） |
| **战绩** | `match` 表按 uid 查，`idx_match_a/b` 索引支持 |
| **回放** | `data/replays/<rid>.json`，DB 存路径。**回放不重跑 LLM**（§2.5），纯 `settle()` 重放 |

## 7. Q7 · 增量改造路线（最重要）

### 7.1 形态矩阵：哪些共用底座，哪些是分叉点

设计侧可能在几种形态间摇摆。**架构必须先说清共用与分叉。**

| 形态 | 共用底座 | 分叉点 | 成本 |

### ADR-007：PvP 通信层采用 SSE 主信道 + REST 命令 + 轮询降级，不引入 WebSocket

- **状态**：提案，待审批
- **背景**：`server.py` 是零第三方依赖的单文件 stdlib 服务（这是它能在 2核2G 上跑、能网盘离线交付的根本原因）。PvP 需要服务器主动推送（回合事件、对手 typing、倒计时）。Python stdlib 无 WebSocket 服务端实现。
- **决策**：
  1. SSE（`text/event-stream` + chunked）作为主信道；客户端命令走现有 REST POST；
  2. 保留 `GET /api/pvp/poll?since_seq=` 长轮询作为降级通道；
  3. SSE 与轮询返回**完全相同的 `EventEnvelope`**（`seq` + `type` + `ts` + `payload`），前端只换 transport；
  4. 现有 REST 接口与 `_send()` 一行不动。
- **后果**：
  - ✅ 零新增依赖；PvP 流量模型（低频上行 / 高频下行）天然匹配单向推送；
  - ✅ 现有单人模式零回归；前端 `EventSource` 是浏览器原生；
  - ✅ 降级成本趋近于 0（共用事件缓冲与解析逻辑）；
  - ❌ 每 SSE 连接占用 1 线程 → 单机上限 ~700 连接（§1.4），超过需改造为 `selectors` 事件循环；
  - ❌ 企业代理 / 部分手机浏览器会缓冲 SSE → 必须实现降级探测（3s 无心跳即切轮询）。
- **被否决的备选**：
  - **手写 WebSocket（stdlib）**：RFC 6455 握手 + 分帧 + 掩码 + 关闭握手 + UTF-8 校验，1.5~2 人日且留长期维护债；全双工省下的连接数在本项目并发量下不构成瓶颈。**收益不足以覆盖成本与风险。**
  - **引入 `websockets` 库**：需 asyncio 事件循环，与现有 threading 模型混用，双运行时心智负担；且打破零依赖硬约束。
  - **FastAPI + uvicorn**：违反「不许重写」铁律。
  - **纯长轮询（不做 SSE）**：实现最简单，但每 2s 一次空轮询在 700 并发下是 350 req/s 的无谓开销，且事件延迟固定为半个轮询周期。**作为主信道不行，作为降级通道很好** —— 故保留。

### ADR-008：PvP 房间状态服务端权威 + `turn_seq` 乐观锁 + `client_msg_id` 幂等

- **状态**：提案，待审批
- **背景**：现有 `_process_message()` (L1420) 持有 session 锁跑完 2 次 LLM（2~4s）。这个模式在单人下可行（一个会话同时只有一个玩家），在 PvP 下（两个玩家并发 × 上百房间）会直接雪崩。同时，网络重试导致的重复提交会重复扣 token —— 在真人对局里这会引发直接纠纷。
- **决策**：
  1. **Room 是唯一权威状态持有者**，客户端只持有 `rid` + `seat_token` + `last_seq`；
  2. **回合锁用乐观锁**：`submit()` 携带 `turn_seq`，服务端校验严格相等，通过后**立即递增 `turn_seq` 并释放锁**；
  3. **锁持有期只包含纯内存操作（<1ms），绝不包含任何 LLM 调用**；LLM 在锁外执行，结果通过 `apply_turn()` 重新取锁提交；
  4. **幂等用 `client_msg_id`**：服务端记 `last_msg_id`，同 id 重放返回缓存响应，**不重复扣 token**；
  5. 三层校验：`turn_seq`（防并发）+ `client_msg_id`（防重试）+ `seat_token`/`expected_side`（防越权）。
- **后果**：
  - ✅ 临界区从 2~4s 压到 <1ms，是 PvP 能撑住并发的唯一可行做法；
  - ✅ 幂等消除了"重复扣 token"这一最易引发真人纠纷的问题；
  - ✅ 沿用现有 `_session_lock` 的 `RLock` 模式，零新概念；
  - ❌ 需要客户端正确生成并携带 `client_msg_id`（UUID4），前端改造成本 0.2 人日；
  - ❌ 乐观锁下失败请求返回 409，前端需正确处理（区分"可重试"与"终态"）。
- **被否决的备选**：
  - **悲观锁（持锁跑完 LLM）**：沿用现有模式、改动最小，但锁竞争在 PvP 并发下会雪崩，且一个慢请求会拖死整个房间。**否决。**
  - **数据库事务锁（`BEGIN IMMEDIATE`）**：把锁下沉到 SQLite。引入磁盘 IO 到关键路径，且 WAL 下的写锁竞争更难调。**否决**（SQLite 只做持久化，不做并发控制）。
  - **无锁 + 后到覆盖**：实现最简单，但会产生状态错乱与双发，**不可接受**。

### ADR-009：所有时限服务端 `monotonic` 判定，客户端计时器纯渲染；掉线 30s 宽限 + 连续 2 回合弃权判负

- **状态**：提案，待审批
- **背景**：客户端计时器可被篡改（改 JS、改系统时间、断网暂停）。同时，国内玩家大量在地铁/电梯/弱网环境游戏，"一断线就判负"会把留存打穿。
- **决策**：
  1. 所有时限存**服务端 `time.monotonic()` 绝对时间戳**（不受 NTP 校时影响）；
  2. 1s 一次 `heartbeat{server_now, deadline_ms}` 下发，客户端**只用于渲染**；
  3. **顺带修复现有缺陷**：`server.py` L1346 `state["start_time"] = time.time()` 改用 `monotonic()`；
  4. **掉线 30s 内可重连**回原房间（凭 `rid + seat_token`），重连后发 `snapshot` + `seq > last_seq` 增量事件；
  5. 超时未提交 → 该回合判弃权（对手气势 +8，自己不扣 token）；**连续 2 回合弃权 → 判负**；
  6. 阈值配置化（`pvp.abandon_grace_s` / `pvp.abandon_strikes`），上线后按数据调。
- **后果**：
  - ✅ 客户端篡改计时器完全无效（服务端是唯一裁判）；
  - ✅ 30s 宽限大幅降低弱网玩家的挫败感，保护留存；
  - ✅ 连续 2 回合才判负，给足了恢复机会，同时防止无限挂机；
  - ✅ `monotonic()` 顺带修掉一个真实的 NTP 跳变 bug；
  - ❌ 需要每房间维持心跳定时器（700 房间 × 1/s = 700 wakeup/s，2 核无压力）；
  - ❌ 30s 宽限意味着对手可能要空等 30s → 需要在 UI 上明确显示"对手断线，30s 后判弃权"。
- **被否决的备选**：
  - **一断线立即判负**：最简单、对手体验最确定，但弱网环境下留存会被打穿。**否决。**
  - **无限宽限（不判负）**：对手会无限空等，且挂机刷分无法处置。**否决。**
  - **客户端上报剩余时间，服务端校验**：形同虚设（客户端可伪造上报）。**否决。**
  - **墙钟 `time.time()`**：NTP 校时会跳变，已有实测风险。**否决。**

### ADR-010：反 AI 代打以玩法设计为主、检测为辅；判定 schema 扩展 `relevance` 零成本取信号；明确不做困惑度检测

- **状态**：提案，待审批（**部分需设计侧配合**）
- **背景**：玩家把题目粘给外部 LLM 再把答案贴回来 —— 对一个「AI 辩论游戏」是致命瓦解。市面上常见的"AI 文本检测"方案在中文短文本上准确率低，且本项目 2核2G 无 GPU。
- **决策**：
  1. **承认 AI 代打无法被可靠检测**，所有技术手段定位为"提高作弊成本"而非"阻断"；
  2. **主战场在玩法设计**（给设计侧）：
     - 🔴 **每回合限时 45~60s（服务端计时）** —— 攻击代打的**操作时间成本**，最强且成本为 0；
     - 🔴 **强制回应对手原话** —— 代打者必须把对手上一轮也喂给外部 LLM，操作成本陡增；
  3. **零增量成本取信号**：在现有单次判定调用的 schema 里加 **`relevance_to_last: 0~1`** 字段（本条发言对对手上一轮的直接回应度）。**不新增任何 LLM 调用**，成本 ≈ +0.00002 元/回合；
  4. 辅助信号：粘贴检测（弱）、输入节奏**聚合**特征（中）、统计指纹打分卡（弱-中）；
  5. 🔴 **明确不做困惑度（PPL）检测**；
  6. 🔴 **禁止采集逐键击键时间戳**（行为生物特征 = 个保法敏感个人信息），只上报聚合特征；
  7. **处置用影子池，不做自动封禁**。
- **后果**：
  - ✅ `relevance` 是本项目独有的强信号，且成本为零 —— 外部 LLM 拿不到本局上下文，这是结构性不对称；
  - ✅ 限时是对代打的降维打击，且**不需要任何检测技术**；
  - ✅ 影子池对真人零误伤、对作弊者是最大惩罚、对运营零人力；
  - ✅ 明确不做 PPL 与逐键时间戳，避免浪费工时与踩合规红线；
  - ❌ 限时会影响"想慢慢组织语言"的玩家体验 → 需要与文策渊一起调阈值（建议 60s 起步，按数据收）；
  - ❌ 检测能力有上限，重度作弊者仍可能漏网 → 接受这个代价，靠影子池隔离污染。
- **被否决的备选**：
  - **困惑度 / PPL 检测**：① 本地需语言模型，2核2G 无 GPU 跑不动；② 云端 API 无 PPL 接口；③ 现代模型上中文 PPL 对"AI 味"判别力已很差。**明确否决。**
  - **调用第三方 AI 文本检测 API**（如天御 AI 生成文本检测 0.05 元/次）：单局 16 次 = 0.8 元/局，**是单局 LLM 成本的 27 倍**，成本不可接受；且对短中文文本准确率存疑。**否决（可作为 1% 抽样的研究手段，不作全量）。**
  - **强制实名 / 设备绑定**：能根治但合规代价过高，且个人主体接不进国家实名系统。**否决（见 §5.5 取舍）。**
  - **自动封禁**：误伤代价高（真人流失）、无申诉人力。**否决，改用影子池。**

### ADR-011：内容安全三层链路 —— 本地前置同步 + 云端机审旁路异步 + 输出侧回扫；1v1 私密才允许旁路

- **状态**：提案，待审批
- **背景**：PvP 把 UGC 风险放大一个数量级（玩家原文直送另一个真人屏幕，且带对喷动机）。但天御同步机审 P95 200~500ms `[待实测]`，串进关键路径会把端到端延迟从 1.65s 推到 2.3s+，且审核服务一抖整个对局卡死。
- **决策**：
  1. **L1 本地前置（同步，<5ms，关键路径）**：敏感词 + 变体（拼音/谐音/繁简/符号分隔）+ 长度 + 纯符号 + 刷屏检测。词表分级 `BLOCK` / `MASK` / `WARN`；
  2. **L2 云端机审（旁路异步，不在关键路径）**：只对灰区调用（中风险词 / 长度异常 / `relevance` 异常 / 该 uid 有前科），结果异步回填做事后处置；
  3. **判定 LLM 与 L1 并行**（L1 通过后立即发起，不等 L2）；
  4. **输出侧本地回扫（同步，<5ms）**：下发到对手前回扫，命中则打码替换；
  5. 🔴 **1v1 私密对局才允许旁路**；**公开观战 / 公开展厅 / 弹幕必须同步前置审核**；
  6. **词表只在服务端，绝不下发前端**；**不提供"还原打码"或"猜词"功能**；
  7. **一键熔断开关**（`off` / `sync_moderation` / `closed`）M0 阶段就要做。
- **后果**：
  - ✅ 端到端延迟不受机审影响（P95 1.65s）；
  - ✅ 审核服务故障不阻塞对局；
  - ✅ 成本可控（灰区 45% 调用率 ≈ 0.0158 元/局，全量则是 0.0352 元）；
  - ❌ 最多 1 条违规内容短暂可见（<1s）→ **仅在 1v1 私密场景可接受**，这也是"公开观战必须同步"的原因；
  - ❌ 词表维护是长期成本（需与文策渊共建，且要定期跑真实语料测误判率）。
- **被否决的备选**：
  - **全量同步前置机审**：最安全，但延迟 +0.3~0.7s、成本翻倍（0.0352 元/局）、且引入审核服务的可用性依赖。**在 1v1 私密场景下过度设计，否决。**
  - **只做本地词表，不接云端机审**：成本 0，但覆盖不了变体与语义级违规（隐晦辱骂、影射），且**不满足《暂行办法》第 14 条的"审核过滤能力"要求**（2026 清朗专项点名整治项）。**否决。**
  - **只审输出不审输入**：玩家输入是最高风险面（可诱导判定 LLM、可写入回放被传播）。**否决。**
  - **把词表下发前端做本地过滤**：等于发一本绕过手册。**否决（红线 #5）。**

### ADR-012：数据层选 sqlite3（WAL + 线程本地连接）；NPC 记忆与天梯进度不迁移，保持 JSON

- **状态**：提案，待审批
- **背景**：现状全部状态在进程内存 + JSON 文件。PvP 需要账号、匹配池、战绩、Elo、回放、举报 —— 关系型需求明确。但硬约束是零第三方依赖，且**任何对单人模式热路径的改动都是回归风险**。
- **决策**：
  1. **选 sqlite3**（stdlib 自带、零依赖、单机部署足够）；
  2. 必开 `journal_mode=WAL` / `synchronous=NORMAL` / `busy_timeout=5000`；
  3. 🔴 **用 `threading.local()` 每线程一个连接**（`ThreadingHTTPServer` 多线程 + `check_same_thread` 默认值，不这么做必然报错）；
  4. 🔴 **NPC 记忆 `npc_state.json` 与天梯进度 `progress.json` 不迁移**，继续用 JSON —— 避免动到 `_finalize_match` / `_gen_memory` / `progress_update` 等单人热路径；
  5. 回放大对象落 `data/replays/<rid>.json`，DB 只存路径；
  6. 匹配池以进程内内存为主，DB 仅 30s 崩溃恢复快照。
- **后果**：
  - ✅ 零新增依赖，符合硬约束；
  - ✅ 写量校验：1,000 DAU 峰值 ≈ 5.6 写/s，SQLite WAL 余量 3 个数量级；
  - ✅ **不迁移 JSON 是关键的降风险决策** —— 单人模式热路径零改动；
  - ✅ 运维成本 0（备份 = 复制文件）；
  - ❌ 单文件写锁 → 锁死单机部署，未来无法水平扩展（本项目 2~3 年内不会遇到）；
  - ❌ 需要 `threading.local()` 连接管理，是个容易踩的坑（已写进实施清单）。
- **被否决的备选**：
  - **继续用 JSON 文件**：PvP 需要按 uid 查战绩、按 Elo 排序、按 rid 查回合 —— JSON 全量读写在并发下必然出问题，且无事务。**否决。**
  - **引入 MySQL / PostgreSQL**：需独立进程 + 运维 + 内存（2核2G 剩不下），且破坏零依赖与离线 demo 交付能力。**否决。**
  - **迁移全部数据到 SQLite（含 NPC 记忆与进度）**：架构更统一，但会动到单人模式热路径，回归风险远大于收益。**否决（明确的"不迁"决策）。**
  - **Redis 做匹配池**：多一个依赖 + 一个进程，2核2G 内存吃紧；匹配量（n<1000）用内存列表完全够。**否决。**

### ADR-013：违规处置必须净亏 —— 打码可做成演出机制，但命中即判 L0 + 文明度惩罚

- **状态**：提案，待审批（**需设计侧确认**）
- **背景**：任务问「打码/屏蔽能否做成游戏机制」。直觉上"被判违规的词变成星号，反而成为演出的一部分"是个漂亮的转化 —— 把合规成本变成玩法资产。但方向错了会变成**激励违规**，这是监管视角下的重大过失。
- **决策**：
  1. ✅ **可以做**，且建议做：①「文明度」第三条资源条；② 打码演出（`██` + "哔——" + 对手获得反击加成，复用现有异议闪屏 VFX 通道，零新增美术）；
  2. 🔴 **约束① 违规必须永远净亏**：打码后该发言**仍判 L0（无效）** + 扣文明度 + **文明度归零判负**。绝不能让骂人有收益；
  3. 🔴 **约束② 词表绝不下发前端**，前端只接收 `{hit, masked_text}`；
  4. 🔴 **约束③ 绝不提供"还原"或"猜词"功能**；
  5. ❌ **不做"嘴臭流"玩法分支**（故意骂人换气势）—— 它会激励违规内容；
  6. 词表分级：`BLOCK`（硬拦）/ `MASK`（打码 + 判 L0）/ `WARN`（只记录）。**M0 只开 BLOCK 的高危政治/色情/暴恐，辩论常见脏话先只 MASK 不 BLOCK**；
  7. 举报原文留存加密 + 访问审计 + 6 个月 TTL；一般调用日志只存 hash。
- **后果**：
  - ✅ 把合规成本转化为玩法资产，且不新增美术成本（复用现有 VFX 通道）；
  - ✅ "文明度"给了设计侧第三条资源条，与气势条 / token 条形成三足；
  - ✅ 明确不做"嘴臭流"，避免激励违规的监管风险；
  - ✅ 词表分级 + M0 只开 BLOCK 高危，把误判风险压到最低；
  - ❌ 误判仍是最大产品风险（"扯淡""放屁""诡辩"是辩论正常表达）→ 必须用天御免费 3,000 条额度跑真实语料测误判率后再调词表；
  - ❌ 打码演出需要前端配合（0.5 人日）。
- **被否决的备选**：
  - **纯拦截（不做打码演出）**：最保守，但浪费了一次把合规转成爽点的机会，且玩家会觉得"莫名其妙被拒答"。**否决。**
  - **打码但不判 L0（内容仍有效）**：等于"骂人的安全出口"，**明确激励违规**。**否决（这是本 ADR 最重要的一条）。**
  - **「嘴臭流」玩法分支（骂人涨气势）**：同上，且会被截图传播形成舆情事故。**否决。**
  - **词表下发前端做实时提示（打字时就提示"这个词会被屏蔽"）**：等于实时提供绕过测试器。**否决。**

## 12. 附：工程控制清单（一页规则，PvP 专项）

> 承接 `harness-architecture.md` §10 的 6 条通用规则，以下是 PvP 追加的 12 条。

1. **PvP 代码优先放新模块**（`demo/pvp/`），能不动 `server.py` 就不动。
2. **单人路径零改动**：PvP 走独立函数；改 `settle`/`schedule`/`judge` 必须有 Golden Test 全等。
3. **房间锁持有期 <1ms**，绝不跨任何 LLM 调用。
4. **`turn_seq` + `client_msg_id` + `seat_token` 三件套缺一不可**，缺任何一个不许上线。
5. **所有时限用 `time.monotonic()`**，客户端倒计时纯渲染。
6. **判定 schema 只加可选字段**，旧调用方必须无感。
7. **词表只在服务端**，前端只收 `{hit, masked_text}`；**不提供还原/猜词**。
8. **违规永远净亏**：打码必判 L0 + 扣文明度。
9. **PvP 题库白名单制**：禁政治 / 地域 / 民族宗教 / 性别对立类命题。
10. **不提供好友 / 私聊 / 自定义昵称 / 公开观战**（M0~M2）。
11. **反作弊只上报聚合输入特征**，禁存逐键时间戳。
12. **PvP 降级 = 无损重试**（不计、不扣、可重发），**绝不用 mock 关键词表兜底**。
