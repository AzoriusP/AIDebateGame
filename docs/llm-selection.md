## 1. 单局 LLM 成本测算模型

### 1.1 测算方法（不是拍脑袋，是实测）

写了只读探针 `demo/tools/token_probe.py`，**不改 `server.py` 一行运行时代码**：

- 复用 `server.py` 里真实的 prompt 构造函数（`_judge_system_prompt` / `_npc_system_prompt` / `_retrospect` / `_gen_memory` / `_generate_hint`）；
- monkey-patch `server._chat`，把每次真实发出的 `messages` 抓下来，返回桩内容；
- 用 `new_session` + `process_message` 驱动完整一局（含局终复盘 + 记忆 + 1 次教练提示），得到逐次调用的真实输入。

**token 换算口径**：中文 **1.5 字/token**、ASCII 4 字符/token，另加消息封装开销 7 token/条 + 3 token 收尾。
> 交叉验证：智谱官方称「GLM 系列 token 与汉字比约 1:1.6」，MiniMax 官方称「1600 中文字符约 1000 tokens」（1:1.6）。取 1.5 属于**略保守**（会高估 token 约 6%），可放心当上界用。若某家分词器实际为 1:1.2，全部成本数字 ×1.25。

### 1.2 单次调用 prompt 实测（字符 → token）

静态 prompt 长度（取 5 个 NPC 实测，含记忆注入）：

| 层 / NPC | 判定 system 字符 | 判定 system token | NPC system 字符 | NPC system token | 是否带记忆 |
|---|---|---|---|---|---|
| L1 王阿姨 | 1,377 | **590** | 2,150 | **1,257** | 是（3 条） |
| L2 林经理 | 1,367 | 584 | 2,025 | 1,175 | 是（1 条） |
| L3 陈博主 | 1,365 | 583 | 1,870 | 1,085 | 否 |
| L4 赵律师 | 1,372 | 587 | 1,877 | 1,088 | 否 |
| L5 陆教授 | 1,365 | 583 | 1,872 | 1,086 | 否 |

整局驱动后的每次调用均值：

| 调用类型 | 单次输入 token | 单次输出 token | 输入中静态前缀占比（缓存可命中部分） |
|---|---:|---:|---:|
| 判定 judge | **644** | 41 | 435 / 644 = **68%** |
| NPC 回复 | **1,525 ~ 1,545** | 67 | 700 / 1,545 = **45%** |
| 教练提示 hint | 529 | 40 | ~60% |
| 局终复盘 retrospect | 1,268（10 回合）→ 2,181（20 回合） | 93 | 不缓存（一次性） |
| 局终记忆 memory | 97 | 33 | 不缓存 |

**关键发现 1**：单回合输入 ≈ 2,190 token，其中 **约 1,780 token 是固定 prompt**（判定 590 + NPC 1,100），玩家实际说的话只占 **27 token**（40 字）。**这是纯 prompt 开销型业务，不是内容型业务 —— 缓存与 prompt 压缩是第一杠杆。**

**关键发现 2**：`npc_reply` 只注入 `history[-6:]`，所以 NPC 输入**不随回合数线性增长**（1,525 → 1,545，几乎持平）。回合数对成本的影响是**线性但斜率很小**的（1 回合 ≈ +2,190 输入 token）。

**关键发现 3（缓存杀手）**：判定 system prompt 里的「六维人格数值」每回合都漂移，NPC system prompt 里的「自信度 / beat / 玩家原话」每回合都变 —— **动态字段目前夹在 prompt 中间，导致后半段全部无法命中前缀缓存**。这是本报告最重要的工程结论（见第 4 节降本手段 #1）。

### 1.3 成本公式

```
单局输入 Token  T_in(N)  = N × 644            # 判定
                         + N × 1545           # NPC 回复（N-1 次，含结尾台词，此处按 N 保守）
                         + 529 + 97            # 教练提示 + 局终记忆（固定）
                         + 1268 + 91 × (N-10)  # 局终复盘（随对话实录线性增长）
单局输出 Token  T_out(N) = N × 41 + N × 67 + 40 + 33 + 93
                         = 108 × N + 166

单局成本（元） C(N) = [ (T_in - T_cached) × P_in + T_cached × P_cache + T_out × P_out ] / 1,000,000
其中  T_cached = (N × 435 + N × 700) × hit_rate        # 静态前缀 × 缓存命中率
      P_in / P_out / P_cache = 输入 / 输出 / 缓存命中单价（元 / 百万 token）

月成本（元）  = C × 局数/月，局数/月 = DAU × 每日局数 × 30
```

**N = 12 回合（典型局）时**：`T_in ≈ 28,200`、`T_out ≈ 1,462`、`T_cached(90%) ≈ 12,300`。

### 1.5 游戏内 token ≠ LLM token（别让大王看混）

| 维度 | 游戏内 token | LLM token |
|---|---|---|
| 是什么 | 玩家发言预算资源（L1=420 → L5=280），UI 上倒计时/见底焦虑的来源 | 模型按量计费单位（1 中文字 ≈ 0.6~0.67 token） |
| 谁消耗 | 玩家：底扣 20 + 超 60 字按 1/字扣，L0 无效发言 +10 | 服务端：每回合判定 ~644 + NPC ~1,545 输入 |
| 量级 | 单局 280~420 **单位** | 单局 24,000~47,000 **token** |
| 换算 | **1 局游戏内 token ≈ 80 LLM token**（420 vs 32,000），差 2 个数量级，**两者无任何换算关系** |
| 优化方向 | 是玩法设计参数，改它 = 改难度 | 是成本参数，改它 = 改账单 |

**一句话**：玩家花的是「口舌」，厂商花的是「算力」，两个 token 同名不同物。给大王看成本时，必须说「单局几分钱」，不能说「单局 420 token」。

- 20 tok/s 下：NPC ~3.4s → 单回合 4.5s，**会明显出戏**。
- **判定是非流式的（ADR-005），TTFT 直接暴露给玩家 → 判定模型必须选低 TTFT 的小模型**。这也是判定不能贪大的第二个理由（第一个是钱）。

### 3.1 「成本会失控」的临界点

**正常的 DAU 增长不会让成本失控** —— 3 分钱一局，1 万 DAU 也就 2.9 万/月。真正的临界点在三个地方：

| 临界点 | 触发条件 | 数字 |
|---|---|---|
| **① 刷量（最大风险）** | 无限流 + 无每日局数上限。一个脚本号：20 回合局约 40~80 秒（2 次调用/回合），理论上**一天可刷约 1,000 局**。1 个号 = 34 元/天；**100 个号 = 3,400 元/天 ≈ 10.2 万元/月** | **从「3 分/局」瞬间变成「五位数账单」** |
| **② 模型档位选错** | NPC 上到 qwen3.8-max / GLM-5.3 这类旗舰档，单局成本 ×9~10 | 1,000 DAU 从 2,889 元 → **2.3~3.3 万元/月**；预算 ¥3,000/月时 **DAU 上限从 ~1,040 掉到 ~110** |
| **③ 预算护栏缺失** | 平台侧不设「每日消费上限 / 免费额度用完即停」 | 任何一次代码 bug（如重试死循环）都会在无人值守的夜里烧穿余额 |

**建议护栏（按此设阈值）**：
- 平台侧：腾讯云/阿里云/火山控制台设 **日消费上限 ¥50**（验证期）→ **¥300**（放量期）；
- 应用侧：**单用户 10 局/天**、**单 IP 30 局/天**、**单局 25 回合硬上限**、**单会话 60 req/min**；
- 应用侧：**全局日消费熔断**，超过阈值自动切到 mock/缓存回复并返回友好提示。

## 4. 降本工程手段（按性价比排序）

性价比 = 省下的钱 ÷ 实现难度 ÷ 质量风险。

| # | 手段 | 预估降本 | 实现难度 | 质量风险 | 说明 |
|---|---|---:|:---:|:---:|---|
| **1** | **prompt 前缀重构 → 打上下文缓存**（把六维数值 / 记忆 / 自信度 / beat / 玩家原话等**动态字段全部挪到 prompt 末尾**，静态规则 + 人设放在最前） | **-25% ~ -35%**（且跨玩家共享前缀可再降） | **低**（只改 prompt 拼接顺序） | 无 | **最高优先级**。当前动态字段夹在中间，导致判定 68% / NPC 45% 的可缓存前缀**全部失效**。改完：判定缓存命中率约 (N-1)/N，NPC 同。并发越高、同一 NPC 对局越多，命中越高。 |
| **2** | **异构模型（判定小 / NPC 大）** | **-20% ~ -70%**（取决于 NPC 原本用多贵的） | **中**（需拆 `JUDGE_MODEL` / `NPC_MODEL`，见第 5 节 #7） | 低 | ADR-001 已天然支持。判定只占成本 24%，用便宜模型；NPC 占 68%，按难度分层。 |
| **3** | **用户级限流 + 每日免费局数 + 全局消费熔断** | **防御性**（不降单价，但直接砍掉 90% 的异常量） | **低** | 无 | 没有这条，其他全部白做。见 3.1。 |
| **4** | **附加调用降级**：局终复盘 / 记忆 / 教练提示 走最便宜模型或 Batch | **-8%** | **低** | 低 | 附加调用占输入 7.4%、输出 11%。记忆（97 输入/33 输出）可改规则模板（已有 `_mock_memory` 兜底逻辑）或异步 Batch。 |
| **5** | **NPC prompt 压缩**（当前 NPC system 1,090~1,257 token，其中「自然度铁律/攻防铁律/输出要求」约 400 token 可精简为分场景注入：不同 beat 只注入对应 1 段） | **-12% ~ -17%** | **中** | **中**（需逐条盲测，压缩过头会掉「人味」） | 只压缩「当前 beat 用不到的指令」是安全的；压缩「自然度铁律」是危险的。**建议只做前者**。 |
| **6** | **上下文窗口 6 → 4 条** | **-4% ~ -5%** | **低** | 中（连贯性下降） | `history[-6:]` 改 `[-4:]`，省约 200 token/回合。收益小，但**顺手做**。更优解：保留 2 条原文 + 1 条滚动摘要（摘要由记忆机制复用）。 |
| **7** | **输出长度硬上限**：`max_tokens` 320 → 200 | **0%（防失控）** | **低** | 无 | 实际输出 ~67 token，平时无影响；但防止模型抽风输出 2,000 token 长文烧钱。**必须加**。 |
| **8** | **分级降级**：免费用户 / 高峰时段走便宜模型，付费或 L4/L5 走贵模型 | **-30% ~ -50%**（按流量结构） | **中** | 低 | 与 #2 共用路由表。高峰时段（19-23 点）自动切 doubao-lite。 |
| **9** | **本地小模型兜底** | 开发期 -100% | **高** | 高 | **生产环境不可行**：腾讯云轻量 2核2G 无 GPU，qwen3.5 9.7B 需 8GB+ 内存，跑不动。仅适合开发期本地 Ollama（现状即如此）。**降级路径应为「小云端模型 / mock」，不是本地模型。** |

**组合效果**：#1 + #2 + #6 三条做完，单局成本 0.032 → **约 0.021 元**（再叠加 #8 可到 0.015 元），1,000 DAU 月成本 2,889 → **约 1,900 元**。

### 5.3 ADR-006 草案：多模型路由与云端接入规范

**状态**：草案，待主理人 / 大王审批
**背景**：ENG-002 选型结论要求「判定与 NPC 用不同供应商的不同模型」，且云端接入引入流式、限流、用量、合规四项新需求。现有 `server.py` 的单模型 + 同步 + 无限流结构无法承载。

**决策**：
1. **D1 异构多模型路由**：判定 / NPC / 附加调用 / 降级 四类角色各自独立配置 `(provider, model, temperature, timeout, max_tokens)`，互不覆盖。`server.py` L57-59 的同构覆盖逻辑必须删除。
2. **D2 供应商抽象层**：统一走 OpenAI 兼容 `/v1/chat/completions`，供应商差异（JSON 模式、缓存开关、usage 字段）由适配层消化，业务层不感知。切换供应商 = 改配置，不改代码。
3. **D3 流式优先**：NPC 回复强制流式（SSE），判定保持非流式（ADR-005 不变）。HTTP 层支持 chunked 或 SSE 下发。
4. **D4 三级降级链**：主模型 → 备用便宜模型 → 规则兜底。降级事件必须埋点并告警，降级率 > 5% 视为 P1 故障。
5. **D5 密钥外置**：API key 只从环境变量读取，永不下发前端、永不写入仓库、永不出现在 `/api/status` 等响应中。
6. **D6 用量与限流内建**：每次调用记录 `usage`；用户级 / IP 级 / 全局三级限流；全局日预算熔断。
7. **D7 缓存友好 prompt 规范**：所有 system prompt 必须「静态前缀在前、动态字段在后」，并在 CI 中加一条检查（动态字段不得出现在静态块之前）。
8. **D8 双向内容安全**：玩家输入与 NPC 输出均过审后才放行，日志留痕 6 个月。

**后果**：
- ✅ 单局成本可压到 0.021~0.032 元，1,000 DAU 月成本 < 3,000 元；
- ✅ 供应商涨价 / 停服时，切换成本 = 改一次配置；
- ❌ 引入流式与 SSE，`server.py` 的 HTTP 层需重写 `_send`，前端需支持增量渲染（工作量约 1~2 人日）；
- ❌ 多一个配置面，需要一份「模型路由表」文档与变更记录。

## 6. 风险与缓解

| 风险 | 触发场景 | 影响 | 缓解措施 | 责任 |
|---|---|---|---|---|
| **API key 泄露** | ①`config.json` 随仓库/截图外流；②前端误下发；③日志打印 header | 账单被盗刷、账号被封 | ①key 移出 `config.json` 到环境变量 + `.gitignore`；②`/api/status` 不再回显 `model`；③日志脱敏（禁止打印 Authorization）；④平台侧设日消费上限；⑤季度轮换 | 主程（P0，接入前必须做完） |
| **被刷量 → 账单爆炸** | 脚本批量开 session 循环发言；无 uid 无配额 | **月账单可达 10 万元级**（3.1 ①） | ①平台侧日消费上限；②单用户 10 局/天、单 IP 30 局/天；③单局 25 回合硬上限、60 req/min；④全局日预算熔断后自动切 mock；⑤关键节点接微信登录/验证码 | 主程（P0） |
| **供应商涨价 / 停服** | 2026 已发生：DeepSeek 8/17 涨价最高 1100%、智谱年内三次提价、Kimi K3 输入涨 3 倍；2026 Q2 国产平均输入价同比 +48%、输出 +80% | 单位成本翻倍，商业模式被击穿 | ①**多供应商路由表（ADR-006 D2）**，切换 = 改配置；②至少保持 2 家已跑通的供应商；③每月复核一次价格，写入变更记录；④成本模型参数化（`demo/tools/token_probe.py` 可重跑） | 主程 + 主理人（季度复核） |
| **境外 API 合规** | 为追求质量接 GPT / Claude / Gemini | **游戏下架 + 行政处罚**（网信办「清朗」专项行动 + 双备案要求） | ①**架构层面禁用**：路由表白名单只允许国产已备案模型；②境外模型仅可在本地开发机做质量对照，禁止写入任何部署配置；③若未来要出海，单独做海外版本与部署 | 主理人拍板，主程执行 |
| **输出违规内容** | 玩家诱导 NPC 谈敏感话题；玩家辱骂/违规输入 | 平台方担责（「技术中立」不构成抗辩） | ①输入侧过审（腾讯云天御/文本安全，价格未核实）；②输出侧过审后再下发；③prompt 内显式安全约束（现有「立场铁律」可复用同一位置）；④扩展 `ATTACK_WORDS` 为违规词表；⑤日志留痕 6 个月；⑥一键熔断开关 | 主程 + 文策（词表） |
| **判定质量不达标（离题检测）** | 换云端后仍漏判离题 | 核心玩法体验崩坏（当前已知问题 #2） | ①判定模型必须过「离题检测专项测试集」（建议 30 条，含同音近义陷阱）；②不达标则升判定档（GLM-5.3-Flash → qwen3.8-flash → doubao-2.0-pro），成本 +0.01~0.07 元/局；③规则兜底：明显跑题（与 topic 关键词零重叠）先走本地判定 | 主程 + 严守真（测试集） |
| **延迟出戏** | NPC 模型 20 tok/s 档 | 单回合 4.5s，玩家流失 | ①判定必选低 TTFT 小模型；②NPC 流式 + 打字机演出（ADR-005）；③高峰时段自动切 highspeed / 更快模型 | 主程 |
| **免费额度到期 / 额度陷阱** | 百炼 90 天过期、火山「每日重置」口径不一 | 验证期后突然开始计费 | ①所有平台开启「免费额度用完即停」开关（阿里云控制台支持）；②日历标记额度到期日；③不依赖免费额度做容量规划 | 主程 |
