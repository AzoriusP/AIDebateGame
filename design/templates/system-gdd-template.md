# 系统 GDD 模板（八节骨架 · 可复用）

> **本文件是可复用空模板。写新系统 GDD 时：复制本文件 → 只保留第 1 节（元信息表）与第 2 节（八节空骨架）→ 填入内容 → 删掉所有「填写指引」灰块 → 按命名规范落盘。**
> 第 3 节是《抬杠模拟器》「六维漂移系统」的**半填充示例**，只用来示范"填完之后长什么样"，不是定稿。

---

## 0. 使用说明

### 0.1 命名规范

```
design/gdd/systems/NN-system-name.md
```

- `NN` = 两位序号，**按域分块**，与 `01-systems-index.md` 的域编号对齐：

| 域 | 序号段 | 示例 |
|---|---|---|
| A 核心玩法 | `00–09` | `05-drift-system.md` |
| B 内容生产 | `10–19` | `11-content-safety.md` |
| C 元系统 | `20–29` | `21-npc-memory-growth.md` |
| D 表现演出 | `30–39` | `30-accessibility.md` |
| F 技术底座 | `40–49` | `40-config-and-value-tables.md` |

- `system-name` = 英文小写、连字符分隔，与系统索引表中的系统名一一对应。
- 序号允许跳号（预留空间），但**一经分配不得复用**。

### 0.2 与总纲 / 索引的引用关系（三句话）

```
00-game-concept.md（总纲 · 只锁方向）
        │  约束：本 GDD 不得违背四条 Design Pillars 与范围边界（总纲 §7.2）
        ▼
01-systems-index.md（索引 · 清单与依赖）
        │  登记：本 GDD 的职责、依赖、优先级、文档状态
        ▼
systems/NN-*.md（本文件 · 规则与数值）
```

**写完一份系统 GDD 后必须做的两件事**：
1. 回 `01-systems-index.md` 把该系统「文档状态」从 `缺口` 改为 `已覆盖：<本文件名>`；
2. 若本文引入了新术语或改了既有术语，回总纲「附录 B · 术语与口径统一」补一行。

### 0.3 五条硬纪律

1. **数值不许写死在正文**。所有数字进 §4 的表格，并注明它是否在 `demo/server.py` / 配置表中已有真值（见 §4 填写指引）。
2. **边缘情况 ≥ 3 类**，且必须包含「AI 失效」类（LLM 超时 / 返回非法 / 被注入）。
3. **验收标准必须可判定**：写"玩家 3 局内能看出软肋在变"，不写"体验良好"。
4. **不确定的写进 §8 待定项并标注原因**，不要编一个看起来合理的数字糊过去。
5. **与既有文档冲突时，不自行改写既有文档**——在 §8 登记为待裁决项，交主理人转大王。

## 2. 八节空模板（含填写指引）

### ① 概述与目标

**本节写什么（1 段 + 1 表）**：这个系统存在的理由、它服务哪条设计支柱、它的成功长什么样。用"如果删掉这个系统，游戏会失去什么"来检验必要性。

- ✅ 该写：一句话职责；对应总纲的哪条 Design Pillar；删掉它的后果；本系统的边界（不负责什么）。
- ❌ 不该写：具体规则与数值（那是 ② 和 ④）；实现方案（那是架构文档）。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：「六维漂移系统负责让 NPC 的软肋在对辩中持续变化，直接服务支柱 2『对手是活的』。删掉它，玩家背住一条软肋就能通关，本作退化为数值解谜。本系统**不负责**跨局的长期成长（那是 C4 NPC 成长系统）。」

**❌ 坏**：「本系统非常重要，是本作的核心创新点，需要重点设计。具体实现见下文。」（没说清职责，也没说边界，"重要"不是信息。）
</details>

```
【一句话职责】

【对应设计支柱】总纲 §4.2 第 <N> 条「<支柱名>」

【删掉它会失去什么】

【本系统不负责什么】（划清与相邻系统的边界）
```

### ② 核心机制（规则 / 状态 / 流程）

**本节写什么**：谁在什么时机、按什么规则、改变什么状态。给状态机或流程伪代码，给规则的完整枚举。规则要能"照着实现"，不能靠读代码的人脑补。

- ✅ 该写：触发时机；输入/输出；规则逐条枚举（含优先级与互斥关系）；状态字段与取值范围；完整流程图或伪代码。
- ❌ 不该写：具体数字（放 ④）；前端怎么画（放 ③⑤）；LLM prompt 全文（放附录或外链）。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：
```
触发时机：每回合结算阶段，判定结果（维度 × 强度）已产出后，顺序执行以下三条，互不冲突：
 R1 警觉上浮：若本回合命中【软肋】且自信度变化达「有效命中」阈值 → 该维漂移值 += 警觉系数 × 该 NPC 的警觉乘数
 R2 强项加固：若本回合命中【强项】 → 该维漂移值 += 加固系数

 R4 钳制：任一维漂移累计值钳制在 ±上限内
```

</details>

### ③ 玩家交互与 UX

**本节写什么**：玩家**看见什么、做什么、拿到什么反馈**。重点是反馈的可归因性——玩家必须能回答"刚才发生了什么、为什么"。

- ✅ 该写：玩家的输入方式；每次变化的即时反馈（视觉/文案/数值标签）；玩家据此能做出什么决策；关键屏幕的布局要点。
- ❌ 不该写：完整视觉规范（那是美术圣经，引用即可）；具体像素/色值（除非必要）。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：「每回合结算后，雷达图上被命中的维度闪一次高亮并浮出标签 `情感 · L2 · 命中软肋`；软肋上浮时该轴显示向外的箭头 + 纹理由虚变实。玩家据此的判断是：'这条打过两次了，该换了'。」

**❌ 坏**：「界面上会有一个雷达图，玩家可以看到六维的变化。」（不可验收：没说反馈是什么、玩家能推断出什么。）
</details>

```
【玩家输入】

【即时反馈】（触发条件 → 玩家看到/听到什么 → 玩家能推断出什么）
| 事件 | 反馈 | 玩家据此的决策 |

【关键屏幕 / 布局要点】（引用美术圣经，不自造视觉规范）
```

### ④ 数据结构与数值

> ⚠️ **硬性要求：数值一律放进本节表格，或从外部单一数据源外链引用，禁止写死在正文或代码逻辑里。**
> 三种合法写法，按优先级：
> 1. **外链真值源**（最优）：`数值见 demo/server.py 顶部常量区 / data/*.json / 配置表 vX`，本文只写变量名与含义；
> 2. **表格 + 状态标注**：表内每行标注 `[实装值]` / `[推荐值-待校准]` / `[已废弃]`；
> 3. **公式**：写变量名、单位与量纲，不写魔数。
>
> 禁止出现：正文里孤零零一个数字、代码里硬编码的常量、同一数值在两处文档各写一遍。

- ✅ 该写：字段名与类型；数值表的**来源标注**；公式的变量与单位；数值之间的约束关系（如"衰减必须快于增长，否则会滚雪球"）；校准方法（用哪个脚本/指标调）。
- ❌ 不该写：prompt 全文（放附录）；与本节无关的设计讨论。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：
| 参数 | 值 | 单位 | 状态 | 含义 |
|---|---|---|---|---|
| `DRIFT_VIGILANCE` | 0.5 | 维值/次 | `[实装值]` | 警觉上浮基准系数，真值源 `server.py` |
| `DRIFT_CLAMP` | 3.0 | 维值 | `[实装值]` | 单维漂移累计上下限 |

约束：`弃守系数 > 警觉系数`，否则软肋永远不换；`上限 < 软肋阈值到强项阈值的跨度`，否则人格崩坏不可识别。

**❌ 坏**：「漂移大概是 0.5 到 1.5 左右，具体看情况调整。」（无字段名、无单位、无真值源、无约束。）
</details>

```
【数据结构】（字段表：名 / 类型 / 范围 / 必填 / 说明）

【数值表】（含来源标注与状态列）
| 参数 | 值 | 单位 | 状态 | 真值源 |

【公式】（变量名 + 单位 + 量纲校验）

【数值约束与校准方法】（用什么脚本/指标调，调到什么现象为止）
```

### ⑤ 表现与演出

**本节写什么**：这个系统在屏幕上"怎么被演出来"。**引用**美术圣经与音频方向，不重复造规范；本节只写**本系统特有的演出事件与触发条件**。

- ✅ 该写：演出事件清单（触发条件 → 演出内容 → 优先级）；与状态量的映射关系；降级方案（演出关掉后是否仍可读）。

### ⑥ 与其他系统的接口

**本节写什么**：本系统跟谁说话、说什么、格式是什么。**接口写清了，系统之间才不会打架。**

- ✅ 该写：上游输入（谁提供、什么字段、什么时机）；下游输出（谁消费、什么事件/字段）；失败时的接口约定（超时/缺字段怎么办）。
- ❌ 不该写：对方系统内部怎么实现。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：
| 方向 | 对端 | 内容 | 时机 | 失败约定 |
|---|---|---|---|---|
| 入 | F6 结算引擎 | `{dimension, strength, delta_conf}` | 每回合结算后 | 字段缺失 → 跳过本次漂移，不抛异常 |
| 出 | D1 雷达图 HUD | `{dim, drift_delta, current_value}` | 结算事件同帧 | 前端 200ms 内未收到 → 沿用上一帧 |

**❌ 坏**：「和结算系统、雷达图都有交互。」（没说传什么、什么时候传、出错怎么办。）
</details>

```
【上游输入】| 来源系统 | 数据 | 时机 | 缺失时的处理 |
【下游输出】| 消费方 | 事件/数据 | 时机 | 消费方未按预期响应时 |
【与 LLM 的边界】（本系统哪些部分允许 LLM 参与，哪些绝对禁止）
```

### ⑦ 边界情况与失败处理

**本节写什么**：**至少 3 类**，必须包含「AI 失效」类。每类写清：现象 → 判定 → 处理 → 玩家看到什么。

必须覆盖的四类（按本作特性）：
1. **玩家侧异常**：空输入、超长输入、刷屏、注入攻击、离题。
2. **AI 侧异常**：LLM 超时、返回非法 schema、置信度过低、模型不可用。
3. **状态边界**：数值触顶/触底、同一回合多个终局条件同时满足、极端连击。
4. **内容/安全**：敏感话题、NPC 输出违规、立场崩坏（NPC 说"你说得对"认输）。

<details>
<summary>好例子 / 坏例子</summary>

**✅ 好**：「**AI 超时**：裁判 >阈值未返回 → 确定性降级为 L0（离题），token 按底扣计，不阻塞 NPC 回复；玩家看到『（他没太听懂）』+ 该回合正常继续。」
**❌ 坏**：「LLM 挂了的话就重试一下。」（没说几次、降级到什么、玩家看到什么。）
</details>

### ⑧ 验收标准与待定项

**本节写什么**：什么算这个系统做对了（**可判定**），以及什么还没定（**带原因**）。

- ✅ 验收标准：可观测、可测、有阈值，最好能写成一个能跑的检查（脚本 / 试玩三步法 / 日志指标）。

## ① 概述与目标

让 NPC 的六维在**单局之内**随玩家打法动态变化：被打疼的软肋上浮警觉、被冷落的维度下沉露出新破绽、被反驳的强项越辩越固。**直接服务支柱 2「对手是活的」与本作的反抄作业目标。**

删掉它，玩家背住一条软肋即可通关，本作从"读人"退化为"查表"。**本系统不负责跨局的长期成长**（那是 C4 NPC 成长系统，走另一条通道、另一套钳制）。

## ② 核心机制

**触发时机**：每回合 `settle()` 内，自信度与 token 结算之后、无进展计数之前，**顺序执行**，规则间不互斥。

**状态字段**：

| 字段 | 类型 | 范围 | 持有者 | 说明 |
|---|---|---|---|---|
| `drift` | dict[dim, float] | 每维 ±上限 | F1 会话状态层 | 相对初值的累计漂移量，局内有效 |
| `npc.dimensions` | dict[dim, float] | 0–10（只读） | F1 | 六维初值，漂移不改写它 |
| `npc.drift_personality` | `{vigilance_mult, abandon_mult}` | 正浮点 | F1（配置） | 每个 NPC 的漂移节奏差异 |

**规则枚举**（顺序执行）：

```
R1 警觉上浮：命中【软肋】且本回合自信度变化达有效命中阈值
    → drift[dim] += DRIFT_VIGILANCE × vigilance_mult
R2 强项加固：命中【强项】
    → drift[dim] += DRIFT_FORTIFY
R3 弃守下沉：取「漂移后当前最弱 且 本回合未被命中」的维度
    → drift[weakest] -= DRIFT_ABANDON × abandon_mult
R4 钳制：drift[dim] = clamp(drift[dim], -上限, +上限)
R5 方向判定依赖漂移后实际值：_direction() 读 current = base + drift，
   软肋阈值 / 强项阈值据此判定（这是"反抄作业"真正生效的关键）
```

**关键设计（core-loop 漏记，本示例补上）**：R5 —— 方向判定读的是**漂移后的当前值**，不是初始值。这保证"软肋被打 2–3 次后真的不再算软肋"。

## ③ 玩家交互与 UX

| 事件 | 反馈 | 玩家据此的决策 |
|---|---|---|
| 软肋上浮 | 雷达图该轴外推箭头 + 命中热度纹理；轴标签加粗 300ms | "这条打过了，收益在降，该换" |
| 冷落维下沉成新软肋 | 该轴内收箭头 + 虚线纹理 | "那边露出新破绽了" |
| 强项加固 | 该轴填充加深 | "别再硬碰了" |

玩家无需输入，本系统是**被动观察型**；但玩家必须能看出"这张图在动"，否则漂移等于不存在。

## ④ 数据结构与数值

> 真值源：`demo/server.py` 顶部常量区。**本表不复制第二份数字。**

| 参数 | 值 | 单位 | 状态 | 真值源 | 含义 |
|---|---|---|---|---|---|
| `DRIFT_VIGILANCE` | 0.5 | 维值/次 | `[实装值]` | `server.py` | 警觉上浮基准系数 |
| `DRIFT_FORTIFY` | 0.5 | 维值/次 | `[实装值]` | `server.py` | 强项加固系数 |
| `DRIFT_ABANDON` | 1.0 | 维值/次 | `[实装值]` | `server.py` | 弃守下沉基准系数 |
| `DRIFT_CLAMP` | 3.0 | 维值 | `[实装值]` | `server.py` | 单维累计漂移上下限 |
| 软肋阈值 | 4（含漂移余量） | 维值 | `[实装值]` | `server.py:_direction` | 当前值 ≤ 阈值判为软肋 |
| 强项阈值 | 6.5 | 维值 | `[实装值]` | `server.py:_direction` | 当前值 ≥ 阈值判为强项 |

**数值约束（设计意图，调参不可违反）**：
1. `弃守系数 > 警觉系数` —— 否则软肋永远不换，反抄作业失效。
2. `累计上限 < (强项阈值 − 软肋阈值)` —— 否则人格漂移过大，玩家认不出"还是这个人"。
3. 软肋失效节奏目标：连打 **2–3 次**才失效（MEMORY 已记），太快挫败、太慢可抄。

**校准方法**：`demo/playtest.py` 纯数值模拟，可重跑；调参目标是"固定一套话术打到底的通关率显著下降"。

## ⑥ 与其他系统的接口

| 方向 | 对端 | 数据 | 时机 | 失败约定 |
|---|---|---|---|---|
| 入 | A2 判定 / F6 结算 | `{dimension, strength, delta_conf}` | 每回合结算后 | 字段缺失或维度为 NULL → 跳过 R1/R2，仍执行 R3/R4 |
| 出 | A3 自信度方向判定 | 漂移后的 `current_dims` | 下一回合 `_direction()` | 读不到时回退到基础值 |
| 出 | D1 雷达图 HUD | `{dim, drift_delta, current_value}` | 随 `turn_resolved` 事件同帧下发 | 前端未收到 → 沿用上一帧 |
| 边界 | C4 NPC 成长 | **不共享状态**：成长改 `npc_state` 的长期修正，漂移改局内 `drift` | 局终才合并 | 二者必须分层，禁止互相写入 |

**与 LLM 的边界**：**LLM 完全不参与本系统**。漂移是确定性纯函数（ADR-002/003），玩家无法通过话术"说服 NPC 别漂移"。

## ⑦ 边界情况与失败处理

| # | 类别 | 现象 | 判定 | 处理 | 玩家可见反馈 |
|---|---|---|---|---|---|
| 1 | 状态边界 | 某维漂移触顶 | `abs(drift) ≥ DRIFT_CLAMP` | 钳制不再变化；该维若已不是最弱则由 R3 另选 | 箭头停止外推 |
| 2 | 状态边界 | 所有维度同时触底（极端连打） | 无可下沉维度 | R3 跳过，不报错 | 雷达图静止 |
| 3 | AI 侧异常 | 判定降级为 L0（超时/非法 schema） | `dimension == NULL` | 仅执行 R3（仍下沉），不执行 R1/R2 | 该回合无命中高亮 |
| 4 | 玩家侧异常 | 玩家连续刷屏（连续 L0） | `l0_streak` 达阈值 | 漂移照常（时间仍在流逝，软肋仍在换），但玩家未获得命中信息 | 无 |
| 5 | 状态边界 | 本回合命中维恰好也是当前最弱维 | `weakest == dim` | R3 跳过该维（不自我抵消，防"打了又白打"） | 无 |

## ⑧ 验收标准与待定项

**验收标准（可判定）**：

1. **反抄作业有效**：连打同一软肋，第 1 次与第 3 次的命中评级应不同（日志 `hit_stats` 维度分布熵上升，或人工试玩可感知"打不动了"）。
2. **人格不崩**：单局结束时，任一维与初值的偏差不超过累计上限，玩家仍能认出"还是这个 NPC"。
3. **换维有收益**：打不动后换到新浮现的维度，应能重新取得有效命中。
4. **试玩三步法**：① 只打一个软肋连打 5 回合 → 应观察到收益递减；② 换维度 → 应重新有效；③ 全程不改打法 → 应打不赢。
5. **可复现**：同一输入序列跑两次，漂移结果完全一致（纯函数，无随机）。
